# 탐지 → L4 차단 시간 측정 결과 (I2-2)

> 발표 핵심 숫자: **SYN Flood를 탐지한 뒤 5초 안에 정문(gateway)에서 L4로 막는가.** 목표는 상위 계획서 2.8.
> 측정 스크립트: `python -m scripts.net.measure_detect_to_block --scenario s5 --repeat 3` (S5b는 `--scenario s5b`)

## 어떻게 재나

시각은 PC 시계가 아니라 **DB에 남은 기록**으로 잰다. 공격 컨테이너·센서·앱의 시계가 서로 달라도 같은 기준으로 비교하기 위해서다.

| 기호 | 기록 | 뜻 |
|---|---|---|
| T0 | `network_events.observed_at` | 센서가 그 IP의 첫 SYN_FLOOD를 본 시각 |
| T1 | `playbook_runs.ran_at` (그 IP 사건의 첫 `block_l4_ttl` 성공) | 앱이 처음 "막아라"(PENDING_APPLY)를 적은 시각. 기록이 없을 때만 `network_blocks.requested_at`을 쓰고 비고에 적는다 |
| T2 | `network_blocks.applied_at` | fw-agent가 ipset에 넣고 "막았음"(APPLIED)을 보고한 시각 |

| 구간 | 목표 |
|---|---|
| T0 → T1 | ≤ 2000ms |
| T1 → T2 | ≤ 2000ms |
| **T0 → T2 (전체)** | **≤ 5000ms** |

- 실행마다 측정 범위(`.150`~`.199`)에서 아직 차단된 적 없는 **새 출발지 IP**를 쓴다. 같은 IP는 앞 실행의 차단과 "사건당 규칙당 1회" 때문에 다시 잴 수 없다.
- S5 = SYN Flood 단독, S5b = SYN Flood + HTTP 폭주 동시(앱이 바쁠 때도 5초를 지키는지). S5b는 비고에 CR-02 매칭 여부를 적는다.
- 값이 `-`이면 그 시각의 기록이 생기지 않은 것이다(못 잰 것은 "초과"로 센다).
- T1을 `network_blocks.requested_at`으로 재지 않는 이유: S5b처럼 NET-01과 CR-02가 몇 초 간격으로 같은 IP를 막으면, 뒤 요청이 같은 행을 갱신해 `requested_at`을 덮어쓴다(계약서 K7 "만료가 더 늦으면 강한 쪽으로 갱신"). `playbook_runs`는 단계마다 한 줄씩 남아 첫 요청 시각이 사라지지 않는다. `ran_at`은 요청이 끝난 뒤 적히므로 실제보다 약 0.2초 늦다 — T0→T1은 그만큼 불리하게, T1→T2는 그만큼 짧게 잡힌다.
- 아래 표의 10/26 S5b 예행 줄은 이 기준을 적용하기 **전** 값이다(새 기준으로 다시 계산하면 T0→T1 1378 · T1→T2 2426 · 전체 3804).

## 센서 기준과 탐지 범위 (10/29 점검)

**SYN Flood 기준이 두 센서에서 다르다 — 일부러 둔 차이다.**

| 센서 | 규칙 | 기준 | 초당 환산 |
|---|---|---|---|
| Suricata | sid `9000001` | 출발지별 5초에 SYN 100개 | 20개 |
| Scapy | `L4_SYN_PER_SEC` | 출발지별 1초에 SYN 100개 | 100개 |

- 거의 항상 Suricata가 먼저 울린다. Scapy는 심한 폭주를 한 번 더 확인하는 두 번째 근거다.
- 둘 다 `SYN_FLOOD`로 분류돼 같은 NET-01(TTL 차단)로 이어지므로, 숫자를 맞추지 않아도 차단 결과는 같다.
- Scapy 기준을 20으로 낮추면 정상 접속이 몰릴 때 오탐만 늘어난다. Suricata 기준은 `test_a_suricata_rules.py`가 고정하고 있다.

**출발지를 바꾸는 SYN Flood는 알림까지만 한다.** `hping3 --rand-source`처럼 패킷마다 출발지가 다르면 출발지별 기준에 걸리지 않는다. Scapy 측정기는 출발지와 상관없는 전체 SYN 비율(`L4_GLOBAL_SYN_PER_SEC`, 기본 1000)이 넘으면 `docker compose logs l4-detector`에 `[WARN] 전체 SYN 폭주 의심` 한 줄을 10초에 한 번 남기고, guide57부터 같은 순간 `l4.json`에 `GLOBAL_SYN_FLOOD`(`src_ip=0.0.0.0`) 한 줄을 써서 앱이 Slack으로 알리고 처리 작업대에 보인다(계약서 K4·K5). 막을 주소가 하나로 정해지지 않아 차단으로는 잇지 않는다. 실제 방어는 gateway의 SYN cookies(`net.ipv4.tcp_syncookies=1`)가 맡는다.

**출발지 상한을 채워 진짜 공격자를 숨기는 방법을 막는다.** Scapy 측정기는 기록하는 출발지를 `L4_MAX_SOURCES`(기본 50,000)곳까지만 둔다. 예전에는 상한이 차면 새 출발지를 버려, 위조 출발지로 상한을 먼저 채운 공격자가 뒤따르는 포트 스캔을 숨길 수 있었다. 지금은 SYN만 보낸 "확인 안 된" 출발지를 오래 쉰 순서로 내보내고 새 출발지를 받는다. SYN 없는 ACK까지 보낸 "확인된" 출발지는 밀려나지 않고, 기록이 전부 확인된 출발지일 때만 새 출발지를 버린다. 한계: ACK도 위조할 수는 있어서 완벽한 증명이 아니라 공격 비용을 높이는 장치다. 밀어낼 때는 `[WARN] ... 밀어냅니다`가 10초에 한 번 로그에 남는다.

**정문(nginx)이 느린 연결 공격을 제한한다.** 연결을 열어 두고 아주 천천히 보내는 공격(Slowloris)은 SYN이 거의 없고 포트도 하나라 위 측정기에 걸리지 않는다. 그래서 `nginx.conf`가 출발지 IP별 동시 연결을 30개로 제한하고(`limit_conn`, 초과 시 429), 요청 헤더·본문이 10초 안에 오지 않으면 연결을 끊는다. 이 공격을 탐지해 ipset으로 막는 것은 계약서 K4에 새 category가 필요해 이번에 하지 않았다. guide57에서 정문 용량을 늘렸다: 예전에는 `worker_processes`가 없어 1개·`worker_connections` 1024였고 프록시가 손님 연결마다 앱 연결을 하나 더 쓰므로 실제로는 약 512명분이라, IP별 30개 제한을 지키는 공격 상자 17개만으로도 정문이 찼다. 지금은 `worker_processes auto`·`worker_connections 4096`·서버 전체 3000개 상한(`limit_conn lw_total`)·`keepalive_timeout 15s`·`reset_timedout_connection on`이다.

**L3 경보(guide57).** ICMP 폭주는 Suricata `rules/l3.rules`의 sid 9000005(출발지별 1초 ICMP echo 200개)가 `ICMP_FLOOD`(L3)로 잡고, 정문 커널의 raw 표 `LW_L3` 체인이 출발지별 초당 50개·전체 초당 2000개 넘는 ICMP를 버린다(주소 차단 없음). edge 대역 밖 출발지가 edge로 들어오면 위조가 확실하므로 Scapy가 10초에 10개 이상일 때 `SPOOFED_SRC`(L3)로 알린다. Scapy의 받는 패킷 조건은 `ip and ((tcp and dst host <.10>) or (not src net <edge>/24 and not src net 172.30.0.0/24))`로 바꿔, gateway가 내보내는 응답 TCP는 더 이상 파이썬으로 올리지 않는다. 세 경보 모두 출발지를 믿을 수 없어 차단·교차 규칙에 쓰지 않고 기록·알림만 한다.

**ET Open 규칙은 이 실습망에서 거의 울리지 않는다.** `entrypoint.sh`가 `HOME_NET`에 edge 대역 전체(`${LW_EDGE_PREFIX}.0/24`)와 core 대역을 넣는다. 공격 상자(`.101`~`.103`, 일회용 `.111` 등)도 edge 대역이라 `HOME_NET` 안에 있고, ET Open 규칙 대부분은 `$EXTERNAL_NET -> $HOME_NET` 모양이라 공격 상자 트래픽에 맞지 않는다. 그래서 실습망에서 실제로 쓰이는 규칙은 `local.rules`(9000001·9000003·9000004)다. ET Open은 실제 외부망 앞에 센서를 둘 때를 위한 것이다. PC마다 다른 edge 대역을 같은 설정으로 쓰려고 대역 전체를 넣은 것이므로 그대로 둔다.

**10/26 실측 요약** (시연 대역 `172.28.0` PC, 각 3회): S5 전체 중앙값 **3227ms**(최대 4149) · S5b 전체 중앙값 **2587ms**(최대 2759) — 6회 모두 전체 5초 이내. S5 1회(.154)는 T1→T2가 2694ms로 구간 목표(2초)만 넘었다(fw-agent 2초 폴링 때문에 0.3~2.7초로 흔들림). 플레이북 `SKIPPED` 0건. 예행 2줄은 실측에 넣지 않는다.

**10/29 재측정 요약** (guide57 보완 후, 시연 대역 `172.28.0` PC, 각 3회): 전체(T0→T2)는 S5 중앙값 **3900ms**(최대 4307) · S5b 중앙값 **3097ms**(최대 **7176**) — 6회 중 5회 5초 이내, S5b 1회(.166)는 앱이 차단을 요청하기까지(T0→T1)만 약 5.8초 걸려 실제로 초과했다(같은 IP의 HTTP 폭주로 앱이 바쁜 상황, 10/26 예행에서도 이 구간이 3.4초까지 늘었다). 재측정 권장.

# 40단계 — 이메일 인증 + 이메일 변경 보호 (비밀번호 찾기의 토대)

[◀ 39단계](guide39_account_enumeration.md) · [전체 목차](beginner-guide.md) · [41단계 ▶](guide41_password_reset.md)

> 다음 단계의 **비밀번호 찾기**는 "계정을 되찾는 메일"이라, 그 메일이 가는 주소가 정말 회원 본인 것이어야 합니다. 그런데 지금까지 가입 이메일은 형식만 검사했고, 이메일 변경은 **로그인 세션만 있으면 비밀번호 확인도 없이** 바로 됐습니다. 이 단계에서 이메일을 "확인된 주소"로 만들고, 이메일 변경을 보호했습니다.

> ⚠️ **배포 전에** Supabase SQL Editor에서 [docs/migrations/guide40_email_verification.sql](../migrations/guide40_email_verification.sql)을 먼저 실행해야 합니다. 새 표가 없으면 회원가입·회원 화면이 오류를 냅니다.

## 무엇이 문제였나

| 문제 | 결과 |
|---|---|
| 가입 이메일을 확인하지 않음 | 오타 주소가 그대로 저장되면 비밀번호를 잊었을 때 되찾을 방법이 없음. 남의 주소로 가입하면 진짜 주인은 그 주소로 가입할 수 없음(이메일 선점) |
| 이메일을 세션만으로 바로 변경 | **세션 탈취 → 이메일을 공격자 주소로 변경 → (비밀번호 찾기로) 비밀번호 재설정 → 계정 탈취**. 영구 잠금 복구 메일도 바뀐 주소로 감 |
| 프로필에서 "이미 다른 회원이 사용 중인 이메일입니다" | 로그인한 회원 누구나 남의 이메일 가입 여부를 확인할 수 있음 |

## 이메일 상태 3가지

| `users.email_status` | 뜻 | 어떻게 되나 |
|---|---|---|
| `UNKNOWN` | 아직 확인 안 됨 (**기존 회원 전부**) | 대시보드에 "이메일 인증이 필요합니다" 안내 |
| `VERIFIED` (신규) | 메일함 주인임이 확인됨 | 비밀번호 재설정 메일을 받을 수 있음(41단계) |
| `UNDELIVERABLE` | 메일 서버가 수신자를 영구 거부 | "메일이 전달되지 않습니다 — 이메일을 변경해주세요" |

**메일 링크를 눌렀다는 것 자체가 그 메일함의 주인이라는 증거**입니다. 그래서 아래 어느 링크를 눌러도 `VERIFIED`가 됩니다.
- 가입/대시보드에서 받은 **인증 메일**
- 이메일 변경 시 새 주소로 받은 **확인 메일**
- 34단계 **영구 잠금 복구** 메일(링크·코드로 복구 성공 시)

## 1. 이메일 인증

```
가입 → 가입 이메일로 인증 링크 발송 (메일이 실패해도 가입은 그대로)
     → 지금처럼 바로 로그인 가능
     → 대시보드: "이메일 인증이 필요합니다 [인증 메일 보내기]"
메일 링크 → 확인 화면(가린 아이디·주소) → [인증] → VERIFIED
```

- **가입은 막지 않습니다**(B 방식). 메일이 늦거나 스팸함에 가도 가입·시연 흐름은 지금과 같습니다.
- "인증 메일 보내기"는 회원·용도별 **60초 쿨다운, 하루 5회**(`EMAIL_TOKEN_COOLDOWN_SECONDS`, `EMAIL_TOKEN_MAX_PER_DAY`).
- 메일 서버가 수신자를 영구 거부(5xx)하면 `UNDELIVERABLE`로 표시합니다.
- 인증 메일을 보낸 뒤 이메일을 바꿨다면, **옛 주소로 간 링크는 새 주소를 인증하지 못합니다**(토큰에 주소를 함께 저장하고, 지금 이메일과 같을 때만 인증).

## 2. 이메일 변경 보호

프로필의 폼을 둘로 나눴습니다.

| 폼 | 동작 |
|---|---|
| 표시 이름 | 지금처럼 바로 저장 (이메일 칸은 없음 — 요청에 `email`을 끼워 보내도 무시) |
| 이메일 변경 | **새 이메일 + 현재 비밀번호** → 새 주소로 확인 링크 → **링크를 눌러야** 변경 |

```
1. 새 이메일 + 현재 비밀번호 [이메일 변경 요청]
   - 비밀번호가 틀리면 로그인 실패로 기록되고 같은 기준으로 잠금(35단계 비밀번호 변경과 동일)
   - 화면: "새 이메일로 확인 메일을 보냈습니다. 메일의 링크를 눌러야 변경됩니다" (항상 같은 문구)
   - 프로필: "확인 대기 중: n*w@…"
2. 새 주소로 확인 링크 (15분, 1회용)
3. 링크 → 확인 화면 → [이메일 변경]
   - 그사이 다른 계정이 그 주소를 차지했으면 실패(기존 이메일 유지)
   - 성공하면 이메일 변경 + VERIFIED
4. 기존 주소로 알림: "이메일이 n*w@…로 변경되었습니다. 본인이 아니라면…"
```

### 이미 다른 계정이 쓰는 주소라면

화면에는 **똑같이** "확인 메일을 보냈습니다"라고 답하고, 그 주소로는 확인 링크 대신 "이 주소는 이미 다른 계정에 등록되어 있어 변경할 수 없습니다"라는 안내 메일만 보냅니다. 그 안내를 읽는 사람은 그 주소의 주인뿐이므로, 화면으로는 남의 이메일 가입 여부를 알 수 없습니다([39단계](guide39_account_enumeration.md)와 같은 원칙). 처리 과정도 같게 만들려고 이 경우에도 토큰 행을 만들었다가 바로 취소합니다 — 하루 한도·쿨다운에도 똑같이 들어갑니다.

### 왜 비밀번호 + 메일 둘 다인가

| 공격자가 가진 것 | 현재 비밀번호만 요구 | 새 주소 확인 메일까지 요구 |
|---|---|---|
| 세션만 | 막힘 | 막힘 |
| 세션 + 비밀번호 | **통과** | 공격자 메일함으로 확인은 되지만, **기존 주소로 변경 알림**이 가서 주인이 알아챔 |
| 본인의 오타 | 오타 주소가 저장됨 | 메일이 안 와서 **반영되지 않음** |

## 3. 링크 처리 — `/email/confirm`

34단계 복구 링크와 같은 원칙입니다.

| 원칙 | 구현 |
|---|---|
| 메일 보안 스캐너가 미리 열어도 안 닳게 | **GET은 확인 화면만**, 실제 처리는 [버튼] POST에서만 |
| 같은 링크가 두 번 처리되지 않게 | 조건부 UPDATE(`status='PENDING' AND expires_at > now()`)로 1회 소비 |
| DB가 유출돼도 링크를 못 만들게 | 토큰은 **SHA-256 해시만 저장** |
| Host 헤더 조작으로 링크 주소 바꾸기 | 링크는 `PUBLIC_BASE_URL`로만 생성 (`helpers.public_base_url()`, 복구 메일과 공용) |
| 무차별 대입 | 토큰은 32바이트 무작위 + POST에 **IP당 분당 10회** 한도(`EMAIL_CONFIRM_RATE_LIMIT_PER_MINUTE`) |
| 메일은 휴대폰에서 여는 경우가 많음 | **로그인 불필요** — 링크를 가진 사람이 곧 메일함 주인 |

토큰은 영구 잠금 복구(`recovery_requests`)와 **다른 표**(`email_tokens`)에 저장합니다. 같은 표를 쓰면 복구의 하루 3회 한도와 대시보드 "복구 요청" 카드에 섞이고, 복구 전용인 기기 쿠키·6자리 코드 흐름과 얽히기 때문입니다. 41단계의 비밀번호 재설정(`PASSWORD_RESET`)도 이 표를 쓰도록 용도를 미리 정의해 두어서, 41단계에는 마이그레이션이 없습니다.

## 4. 관리자 대시보드

회원 목록의 이메일 옆에 **인증됨 / 미인증 / 반송** 배지를 붙였습니다.

## 계획에서 바뀐 점

- 계획에는 이메일 변경 완료 시 보안 이벤트 `EMAIL_CHANGED`(LOW)를 남긴다고 했지만, `security_events.severity`는 MEDIUM 이상만 허용하고(DB 제약), 이메일 변경은 공격이 아니라 정상 행위라서 **보안 이벤트로 남기지 않았습니다**. 대신 `email_tokens` 표에 누가(회원) 언제(`used_at`) 어느 IP에서 요청했는지(`requested_ip`)가 그대로 남고, 기존 주소로 알림이 갑니다.

## 운영상 알아둘 점

- **기존 회원은 모두 미인증(`UNKNOWN`)입니다.** 일괄로 인증 처리하지 않았습니다 — 확인된 적 없는 주소를 확인된 것처럼 다루게 되기 때문입니다. 41단계(비밀번호 찾기)가 배포되기 전에 회원들이 로그인해서 인증해 두어야 합니다. 영구 잠금 복구 메일은 지금처럼 미인증 주소에도 갑니다(반송 주소만 제외).
- 가입 때 메일을 같은 요청 안에서 보내므로 가입 응답이 1~3초 늦어질 수 있습니다(Vercel → SMTP 왕복).
- 회원가입 화면의 "이미 사용 중인 아이디 또는 이메일입니다"는 여전히 가입 여부를 알려줍니다(39단계 남은 위험, 범위 밖).

# 1. 인증 (회원가입 / 로그인)

<aside>
🎯 **한 줄 요약**
회원가입은 "새 출입증을 만드는 일", 로그인은 "출입증을 보여주고 건물에 들어가는 일"입니다. 이 프로젝트는 그 출입문을 **감시하는 시스템**이라서, 이 두 기능이 모든 보안 기능이 올라서는 무대가 됩니다.
</aside>

> 🗺️ **클릭해서 코드를 볼 수 있는 흐름도**: [01-auth.html](01-auth.html) — 카드나 파일 이름을 누르면 실제 코드가 열립니다.
> 📚 **계층**: Layer 1. 기반 기능 (사용자가 직접 쓰는 화면)

<aside>
🖥️ **화면 구조 참고**
이 문서와 흐름도는 **서버(Flask)가 요청을 처리하는 순서**를 따라갑니다. 실제 서비스의 화면은 지금 Next.js로 그려지지만, 폼 제출을 받으면 **같은 `signup_submit()`·`login_submit()`이 그대로 실행**됩니다(화면 ↔ 서버 연결은 30단원). 그래서 흐름도의 `templates/…` 카드는 "화면이 보내는 폼"의 예시로 봐 주세요.
</aside>

## 🏢 비유로 먼저 이해하기

| 현실 | 이 프로젝트 |
|---|---|
| 건물 정문 | 로그인 화면 (`/login`) |
| 출입증 발급 창구 | 회원가입 화면 (`/signup`) |
| 출입증 발급 기록부 | `users` 표 (회원 목록) |
| 출입 기록 CCTV | `login_attempts` 표 (로그인 시도 기록) |
| 경비원 | 서버 (`routes/auth.py`의 함수들) |

<aside>
💡 이 프로젝트가 감시하는 대상이 바로 "로그인"입니다. 감시할 문이 있어야 "누가 문을 계속 두드리는지(브루트포스)" 같은 공격도 잡을 수 있습니다.
</aside>

## ✍️ 회원가입이 일어나는 순서

사용자가 아이디·이메일·비밀번호를 적고 **'가입하기'** 를 누르면, 서버는 계정을 저장하기 전에 **여덟 번의 검문**을 합니다.

| 순서 | 검문 | 쉬운 설명 | 막히면 |
|:-:|---|---|---|
| ① | 가입 접수가 열려 있나? | 관리자가 가입을 꺼뒀는지 확인. 화면에서 숨겨도 직접 요청을 보낼 수 있어서 서버가 한 번 더 확인합니다. | "현재 회원가입이 잠시 중단되어 있습니다." |
| ② | 사람이 맞나? (허니팟) | 사람 눈에는 안 보이는 **숨은 입력칸**이 있습니다. 사람은 못 보니 비워두지만, 자동 프로그램(봇)은 칸을 전부 채우려 해서 걸립니다. | "일시적인 오류가 발생했습니다." |
| ③ | 영구 차단된 네트워크인가? | 영구 잠금된 IP는 가입도 못 합니다. 새 계정을 만들어 예외를 받아내는 우회로를 막기 위해서입니다. | "이 네트워크에서는 회원가입을 할 수 없습니다." |
| ④ | 너무 빨리, 많이 가입하나? | 같은 IP가 **1분 안에 5번 이상** 시도하면 막습니다. | "너무 많은 가입 시도가 감지되었습니다." |
| ⑤ | 이번 시도 기록 | 성공이든 실패든 "가입을 시도했다"는 사실을 한 줄 남깁니다. ④의 횟수가 여기서 쌓입니다. | – |
| ⑥ | 입력값 규칙 검사 | 아이디(영문·숫자·밑줄 3~20자), 이메일 모양, 비밀번호 8자 이상, 비밀번호 확인 일치 | 틀린 항목에 맞는 안내 문구 |
| ⑦ | 계정 저장 | 아이디·이메일이 이미 쓰이는지 확인하고, 비밀번호를 **해시**로 바꿔 저장 | "이미 사용 중인 아이디 또는 이메일입니다." |
| ⑧ | 인증 메일 + 이동 | 가입 이메일로 인증 링크를 보내고(실패해도 가입은 유지) 로그인 화면으로 이동 | – |

<aside>
🔐 **해시(hash)란?** 비밀번호를 **되돌릴 수 없는 암호문**으로 바꾸는 것입니다. 데이터베이스가 유출돼도 원래 비밀번호는 알 수 없습니다. 이 프로젝트는 비밀번호 원문을 어디에도 저장하지 않습니다.
</aside>

## 🔑 로그인이 일어나는 순서

로그인은 **"비밀번호가 맞나?"를 보기 전에** 먼저 잠금·봇 여부를 검문합니다. 이미 잠긴 상대의 비밀번호를 확인해주는 것 자체가 공격자에게 기회를 주기 때문입니다.

| 순서 | 검문 | 쉬운 설명 |
|:-:|---|---|
| ① | 만료된 잠금 청소 | 시간이 지나 풀려야 할 잠금(IP·계정)을 먼저 정리합니다. |
| ② | 사람이 맞나? (허니팟) | 회원가입과 같은 숨은 입력칸 검사. 걸리면 비밀번호 확인도, 기록도 없이 거부합니다. |
| ③ | 이 IP가 잠겨 있나? | 잠긴 IP는 비밀번호를 보지도 않고 거부합니다. **영구 잠금 IP**는 이메일 복구로 예외를 받은 "본인 + 본인 기기"만 통과합니다. |
| ④ | 이 계정이 잠겨 있나? | 여러 IP가 돌아가며 한 계정을 공격하는 경우를 대비한 **계정 단위** 잠금 확인. |
| ⑤ | 아이디·비밀번호 확인 | 저장된 해시와 입력한 비밀번호를 비교합니다. |
| ⑥ | 시도 기록 | **성공이든 실패든** 누가 어떤 IP에서 시도했는지 한 줄 남깁니다. |
| ⑦ | 성공했나? | 길이 둘로 갈라집니다. |
| ✅ | 성공 | 브라우저에 "로그인된 상태"를 기억시키는 **세션**을 만들고 회원 대시보드로 이동합니다. |
| ❌ | 실패 | 항상 **같은 문구**로 안내하고, 이 IP·계정의 실패가 기준치를 넘었는지 판정합니다(→ 5단원). |

<aside>
🕵️ **왜 실패 문구가 항상 똑같나요?**
"아이디가 없습니다"와 "비밀번호가 틀렸습니다"를 구분해서 알려주면, 공격자가 *"이 아이디는 실제로 존재하는구나"* 를 알아낼 수 있습니다. 그래서 어떤 경우든 "아이디 또는 비밀번호가 올바르지 않습니다."라고만 합니다.
</aside>

<details>
<summary>⏱️ <b>응답 시간으로도 힌트를 주지 않아요 (타이밍 사이드채널 방지)</b></summary>

비밀번호 비교는 일부러 **느리게** 설계된 계산입니다. 만약 아이디가 없을 때 이 계산을 건너뛰고 바로 실패를 알려주면, 공격자는 *"즉시 실패 = 없는 아이디, 약간 느린 실패 = 있는 아이디"* 라는 **시간 차이**만으로 아이디 존재 여부를 추측할 수 있습니다.

그래서 없는 아이디일 때도 **미리 만들어둔 가짜(더미) 해시**와 똑같은 비교를 한 번 거쳐서, 어느 경우든 걸리는 시간이 비슷하게 만듭니다. 이 방어는 15단원(L7 공격 방어 보강)에서 다시 다룹니다.
</details>

## 📍 코드는 어디에 있나요?

이 표의 파일 이름을 흐름도(`01-auth.html`)에서 클릭하면 해당 함수의 실제 코드를 바로 볼 수 있습니다.

| 하는 일 | 파일 | 함수 |
|---|---|---|
| 가입 화면 모양 | `templates/signup.html` | (HTML 폼) |
| 로그인 화면 모양 | `templates/login_form.html` | (HTML 폼) |
| 가입 요청 처리 (검문 순서 지휘) | `routes/auth.py` | `signup_submit()` |
| 로그인 요청 처리 (검문 순서 지휘) | `routes/auth.py` | `login_submit()` |
| 봇 함정 확인 | `helpers/request_utils.py` | `is_bot_submission()` |
| 가입 도배 판정 | `security/detector.py` | `is_signup_rate_limited()` |
| IP·계정 잠금 판정 | `security/detector.py` | `is_locked()`, `is_account_locked()` |
| 가입 허용 여부 읽기 / 가입 시도 기록·집계 | `db/settings.py` | `get_signup_enabled()`, `log_signup_attempt()`, `count_recent_signup_attempts()` |
| 계정 저장 | `db/users.py` | `create_user()` |
| 아이디·비밀번호 확인 | `db/users.py` | `verify_user_credentials()` |
| 로그인 시도 기록 | `db/attempts.py` | `log_attempt()` |
| 아이디·이메일·비밀번호 규칙값 | `config.py` | `USERNAME_PATTERN`, `EMAIL_PATTERN`, `MIN_PASSWORD_LENGTH` |

<aside>
🧭 **코드에 `db.create_user()`라고 적혀 있는데 `db` 폴더에서 못 찾겠다면?**
`db/__init__.py`는 "창구" 역할만 하고, 실제 함수는 `db/users.py`, `db/attempts.py` 같은 파일에 나뉘어 있습니다. 흐름도는 이 연결을 **`db.create_user()` → `db/__init__.py`(창구) → `db/users.py`** 로 풀어서 보여줍니다.
</aside>

## 📖 용어 사전

<details>
<summary><b>세션(session)</b></summary>

서버가 "이 브라우저는 이미 로그인한 사람"이라는 사실을 기억하는 저장 공간입니다. 이 프로젝트의 회원 세션은 관리자 세션과 **다른 이름표**를 써서, 같은 브라우저에서도 서로 섞이지 않습니다.
</details>

<details>
<summary><b>허니팟(honeypot)</b></summary>

"꿀단지" 함정입니다. 사람 눈에는 안 보이는 입력칸을 숨겨두고, 거기에 값이 들어오면 사람이 아니라 자동 프로그램이라고 판단합니다.
</details>

<details>
<summary><b>브루트포스(brute force)</b></summary>

비밀번호를 하나씩 계속 넣어보는 무차별 대입 공격입니다. 이 프로젝트의 탐지 기능(5단원)이 막는 대표 공격입니다.
</details>

<details>
<summary><b>POST 요청</b></summary>

브라우저가 입력한 내용을 서버로 "제출"하는 방식입니다. 주소만 방문하는 것(GET)과 구분됩니다. `/signup`, `/login`은 방문하면 빈 폼이 보이고, 제출하면 처리가 시작됩니다.
</details>

## ⚠️ 알아둘 한계

- 이메일 형식 검증은 "이메일처럼 생겼는지"만 봅니다. 실제로 받을 수 있는 주소인지는 **인증 메일**로 확인합니다(23단원).

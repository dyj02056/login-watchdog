# 50단계 — 7일치 샘플 로그 만들기 (대시보드 시연용)

[◀ 49단계](guide49_scripts_reorganization.md) · [전체 목차](beginner-guide.md)

> 기능은 그대로이고, 시연·스크린샷용 도구를 추가했습니다. 내 컴퓨터에서 **진짜 서버를 켜고, 가짜 회원을 가입시키고, 공격 시뮬레이션 21종을 돌려서** 지난 7일치 기록을 만들고, 그 기록으로 대시보드를 띄웁니다. 원하면 같은 기록을 실제 Supabase에도 넣을 수 있습니다.

## 왜 만들었나

예전 `demo_server.py`는 **손으로 쓴 가짜 숫자**를 화면에 끼워 넣었습니다. 그래서 "영구 잠금인데 근거 이력이 없다"처럼 서로 앞뒤가 안 맞을 수 있었고, 새 기능(AI 조기경보, 연관 사건, 영구 잠금)이 화면에 실제로 어떻게 보이는지 확인하기 어려웠습니다.

이제는 기록을 지어내지 않고 **서버가 직접 만들게** 합니다. 잠금·사건·조기경보가 실제 규칙대로 연결되므로 시연 화면이 실제 운영 화면과 같은 모양이 됩니다.

## 한 줄 요약

```
서버 켜기 → 회원 가입 → (정상 접속 + 공격 21종)을 시각 순서대로 실행 → 시각을 지난 7일로 옮기기 + IP를 여러 나라 것으로 바꾸기 → JSON 저장 → 대시보드로 보기
```

## 파일 구성 (`scripts/demo/`)

| 파일 | 역할 |
|---|---|
| `generate_demo_logs.py` | 샘플 로그를 만들어 `scripts/demo/output/demo_logs.json`에 저장 |
| `demo_server.py` | 그 JSON으로 대시보드를 띄움 (`http://127.0.0.1:5077`) |
| `load_demo_to_supabase.py` | (선택) 실제 Supabase에 넣거나(`--apply`) 지움(`--purge`) |
| `demo_data.py` | 나라별 IP 대역, 가짜 회원 이름, 시각 이동 규칙 |
| `memory_supabase.py` | 메모리 가짜 DB(49단계). 이번에 보완함 |

`output/` 폴더는 `.gitignore`에 들어 있어 깃에 올라가지 않습니다.

## 만들어지는 과정

1. **준비** — 메모리 DB를 붙인 서버를 로컬 5000번 포트에 켭니다. `.env`의 Supabase 주소는 존재하지 않는 값으로 덮어써서 진짜 DB에는 접속할 수 없고, Slack·메일도 보내지 않습니다.
2. **회원가입** — 가짜 회원 12명을 실제 `/signup` 화면으로 가입시킵니다(9명은 7일 이전, 3명은 이번 주 가입). 이후 실제 로그인·글쓰기·댓글을 하고, 가끔 비밀번호를 틀립니다. 관리자 계정 3개(최고 관리자·보안 관리자·조회 전용)도 만듭니다.
3. **실행 계획** — 공격 21종을 한 번씩은 반드시 넣고, 반복 공격자 3명(같은 IP가 여러 날 돌아옴), 같은 계정을 두 번 노리는 분산 공격, 무작위 추가 14건, 임계값 바로 아래까지만 두드리는 조기경보용 변형, 방금 일어난 공격 5건을 더합니다. 날짜는 돌아가며 배정해 7일에 고르게 퍼뜨리고, 시각은 새벽에 몰리게 합니다.
4. **시각 순서대로 실행** — 묶음 하나가 끝날 때마다 (a) 그 묶음이 만든 기록의 시각을 배정된 시각으로 옮기고(공격 안의 앞뒤 순서는 유지) (b) 시뮬레이션이 스스로 쓴 IP를 여러 나라의 IP로 바꿉니다. 윈도우 소켓 고갈 같은 일시 오류가 나면 그 묶음이 만든 행을 되돌리고 다시 시도합니다.
5. **마무리** — 일별 요약표(`log_daily_summary`, `log_daily_breakdown`)를 만들고, 오래된 사건·이벤트·조기경보의 일부를 관리자가 처리한 것으로 만듭니다. 이메일 복구 요청·IP 예외를 채우고, 대시보드에 `-`로 보일 칸을 채운 뒤 JSON 한 파일로 저장합니다.

공격 시뮬레이션 21종은 다음과 같습니다.

| 위험도 | 시뮬레이션 |
|---|---|
| CRITICAL | 브루트포스, 패스워드 스프레이, 분산 브루트포스, 관리자 브루트포스, 관리자 분산 브루트포스, 영구 잠금, 사건 상관분석 |
| HIGH | 회원가입 도배, 게시글 도배, 댓글 도배, HTTP 폭주, 복구 요청 폭주 5종 |
| MEDIUM | 웹 스캐닝, 무단 접근, 반복 페이지 접근, 매크로/API 봇, 허니팟 봇 |

## 여러 나라 IP

- 러시아·중국·미국·독일·브라질·인도·베트남·한국·일본·영국·프랑스·네덜란드·인도네시아·터키·나이지리아·캐나다·호주, **17개국**입니다.
- 각 나라에 실제로 할당된 대역의 앞 두 칸을 쓰고, 뒤 두 칸만 무작위로 고릅니다. **이 주소로는 어떤 접속도 하지 않습니다.** 우리 서버의 요청 헤더(`X-Forwarded-For`)와 DB 값으로만 들어갑니다.
- 정상 회원은 대부분 한국에서, 분산 공격은 서로 다른 나라의 IP를 섞어 접속합니다.
- 국가 조회는 외부 서비스(ip-api.com)를 부르지 않고, 미리 만든 위치표를 `ip_locations` 캐시에 넣어 처리합니다. 인터넷이 없어도 되고 호출 한도도 신경 쓸 필요가 없습니다.
- 대역 정보는 공개 할당 정보를 바탕으로 직접 고른 값이라, 외부 위치 조회 서비스에서는 도시가 다르게 나올 수 있습니다. 화면의 "공격자"는 실제 공격자가 아닙니다.

## AI 조기경보

임계값 코앞에서 AI에게 "지켜볼 필요가 있는지" 묻고, 위험하면 관리자 승인 대기 요청을 만드는 기능([guide31](guide31_llm_judgment_agent.md))입니다.

- **기본**: 로컬 판정기를 씁니다. 인터넷과 API 키가 필요 없고 외부 접속이 없습니다. 대부분 "위험", 일부는 "정상"으로 판정하고, 사유는 고정 문장 템플릿입니다.
- **`--use-groq`**: 진짜 Groq API로 판정합니다. `.env`의 `GROQ_API_KEY`가 필요하고(없으면 안내 후 종료), **샘플 IP·아이디·횟수가 Groq로 전송됩니다.** 그 밖의 외부 접속은 계속 막혀 있습니다. 끝날 때 `호출 N회 · 위험 · 정상 · 실패` 요약을 출력합니다. 호출이 50건 안팎이라 무료 한도(429)에 걸리면 느려지거나 일부가 실패할 수 있고(실패한 건은 조기경보가 만들어지지 않음), 같은 `--seed`여도 응답이 달라질 수 있습니다.

## `-`(빈칸) 줄이기

대시보드가 값이 없을 때 `-`로 그리는 칸을 코드에서 찾아, 의미가 맞는 범위에서 채웠습니다.

| 칸 | 채우는 방법 |
|---|---|
| 국가·접속 위치 | 모든 IP의 위치를 캐시에 미리 채움 |
| 대상 경로 | 이벤트 유형에 맞는 대표 경로(`/login`, `/admin/login`, `/signup` 등) |
| 계정 | 같은 IP가 그 무렵 시도하거나 로그인한 계정 |
| 처리자·처리 시각 | 처리된 건에만 (진행 중인 건은 비워 둠) |
| 잠금 사유·복구 방법 | 영구 잠금에는 항상 |

원래 비어 있어야 정상인 칸(진행 중 건의 처리자)과 맞는 값이 없는 칸(로그인 없는 웹 스캐닝의 계정)은 `-`로 남습니다.

## 사용법

가상환경을 켠 뒤(터미널을 열 때마다 한 번, 프로젝트 루트에서) 실행합니다.

```powershell
.\venv\Scripts\Activate.ps1
```

```bash
source venv/Scripts/activate   # Git Bash
```

**1) 샘플 로그 만들기 — 처음 한 번, 약 2분**

```bash
python scripts/demo/generate_demo_logs.py
python scripts/demo/generate_demo_logs.py --use-groq     # AI 조기경보를 진짜 Groq로 판정
python scripts/demo/generate_demo_logs.py --seed 7       # 같은 숫자면 같은 결과, 다른 숫자면 다른 순서·모양
```

그 밖의 옵션: `--days 7`(기간), `--members 12`(가입시킬 가짜 회원 수, 최대 12), `--out 경로`(저장할 JSON).

**2) 대시보드 보기**

```bash
python scripts/demo/demo_server.py
```

`http://127.0.0.1:5077/__demo_login`(관리자), `http://127.0.0.1:5077/__demo_member`(회원)을 엽니다. 열 때마다 기록 시각을 "지금" 기준으로 옮겨서(`--no-shift`로 끌 수 있음) 며칠 전에 만든 파일도 항상 최근 7일처럼 보입니다. 아직 풀리지 않은 임시 잠금은 서버를 켠 시각부터 5분 뒤에 풀리도록 맞춥니다.

## (선택) 실제 Supabase에 넣기

```bash
python scripts/demo/load_demo_to_supabase.py            # 미리보기 — 아무것도 쓰지 않음
python scripts/demo/load_demo_to_supabase.py --apply    # 실제 적재 — DB 주소를 직접 입력해 확인
python scripts/demo/load_demo_to_supabase.py --purge    # 넣은 행만 삭제
```

- 확인 질문에는 URL 전체가 아니라 **호스트 이름만**(예: `abcdefgh.supabase.co`) 입력합니다. 다르게 입력하면 아무것도 쓰지 않고 끝납니다.
- 넣은 행의 기본키(번호)를 `output/supabase_manifest.json`에 남기고, `--purge`는 그 번호의 행만 지웁니다(행에 "샘플" 표시를 붙이는 방식이 아닙니다). 이 파일은 내 컴퓨터에만 있으므로, 지웠거나 다른 컴퓨터에서 실행하면 지울 수 없습니다.
- 회원 비밀번호는 로그인할 수 없는 값으로 바꿔서 넣고, 관리자 계정과 메일 토큰은 넣지 않습니다.
- 같은 아이디·이메일의 회원이 이미 있으면 아무것도 넣지 않고 중단합니다. 이미 요약이 있는 날짜의 일별 요약과 이미 있는 잠금·IP 위치 행은 건너뜁니다.
- 글 → 댓글, 사건 → 잠금 이력처럼 서로 가리키는 번호는 새 번호로 이어 붙입니다. 반대로 `--purge`는 외래키 연쇄 삭제의 영향을 받습니다(샘플 글을 지우면 그 글에 달린 댓글도, 샘플 회원을 지우면 그 회원의 복구 요청·이메일 토큰도 함께 지워짐).
- 기존 운영 데이터와 섞이는 것이 부담이면 별도의 빈 Supabase 프로젝트에 넣는 것을 권장합니다.

## 메모리 DB 보완 (`memory_supabase.py`)

샘플 로그를 만들고 읽으려고 가짜 DB를 다음과 같이 보완했습니다. 49단계의 `check_simulations.py`는 그대로 22/22 통과합니다.

- **표마다 실제로 있는 시각 칸만 채웁니다.** 예전에는 모든 행에 `attempted_at`·`detected_at` 같은 칸을 전부 붙여서, 진짜 DB에 넣으면 "없는 칸" 오류가 났을 것입니다.
- **진짜 DB가 `default`로 채우는 값**(회원의 `email_status`, 잠금의 `lock_type`, 이벤트의 `resolved_at`=비어 있음 등)을 넣습니다. 없으면 대시보드가 `KeyError`로 죽었습니다.
- `access_requests`의 기본키가 `request_id`인 것, `select(..., head=True)`, `users(username)` 연결 조회를 지원합니다.

## 한계와 주의

- IP 대역은 직접 고른 값이라 외부 조회 서비스와 도시가 다를 수 있습니다.
- 이메일 복구 요청·IP 예외는 메일 인증 코드를 사람이 입력해야 해서 서버 흐름이 아니라 직접 만든 행입니다.
- 임시 잠금은 실행 중에는 3초(영구 잠금 시뮬레이션이 5분을 기다리지 않게)로 돌리고, 저장할 때 기록상 5분으로 고칩니다.
- 시뮬레이션 한 번이 만드는 이벤트 수가 서로 달라서 날짜별 건수가 고르지는 않습니다.
- 실행 로그에 `FAIL`로 보이는 조기경보용 변형(`ew_*`)은 일부러 잠금 직전까지만 두드려 시뮬레이션 자체는 실패로 끝나는 것이며 정상입니다. 가입한 회원 중 한 명이 공격으로 잠겨 로그인되지 않는 접속이 한 건쯤 생길 수 있습니다.
- `load_demo_to_supabase.py`는 메모리 DB를 대상으로 한 테스트까지만 검증했고, 진짜 Supabase에 대해서는 사용자가 직접 실행해 확인해야 합니다. `--use-groq`도 실제 호출은 사용자가 직접 확인해야 합니다.

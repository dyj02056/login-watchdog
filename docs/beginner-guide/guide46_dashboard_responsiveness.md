# 46단계 — 대시보드 즉시 반응

[◀ 45단계](guide45_visible_tab_polling.md) · [전체 목차](beginner-guide.md) · [47단계 ▶](guide47_daily_log_summary.md)

> 대시보드에서 버튼을 누르면 2초 넘게 아무 반응이 없었습니다. 버튼 하나를 누를 때마다 **대시보드 전체**(표 8개 + 카드 6개, DB 조회 약 21번)를 처음부터 다시 받아왔기 때문입니다. 이번 단계에서 세 가지를 바꿨습니다. **누르는 즉시 화면이 반응**하고(A), **페이지를 넘길 때는 그 표 하나만** 받아오며(B), **전체 갱신 자체도 빨라졌습니다**(C). 같은 작업 중에 발견한 "페이지 번호가 음수로 내려가는" 버그도 고쳤습니다. DB 스키마 변경은 없습니다.

## 문제

운영 로그에서 `/api/status` 11건의 처리 시간을 계산했습니다(요청 ID의 시작 시각과 완료 기록의 차이).

| | 처리 시간 |
|---|---|
| 가장 빠름 | 1.60초 |
| **평균** | **2.22초** |
| 가장 느림 | 3.03초 |

- "다음 페이지" 하나를 눌러도 화면 전체를 다시 받았다.
- 원격 DB(Supabase) 조회는 한 번 왕복에 0.15~0.4초가 걸린다. 동시에 보내도 **앞 단계가 끝나야 시작하는 단계**가 여러 개라 차례로 기다렸다.

| 단계 | 내용 |
|---|---|
| 1 | 세션 확인(관리자 계정 조회) |
| 2 | 만료된 잠금 정리 3종 |
| 3 | 화면 데이터 15개. 동시 처리 한도가 12개라 **두 번에 나눠** 감 |
| 4 | "관리자 계정 관리" 카드의 권한 확인 → 목록 (**차례로 2번 더**) |

- 응답이 오기 전에는 화면에 아무 변화가 없어서, 눌렸는지 알 수 없었다. 그래서 다시 누르게 되고 같은 요청이 여러 번 나갔다.

**함께 발견한 버그:** "← 이전"을 응답 전에 빠르게 연달아 누르면 페이지 번호가 0, -1, -2…로 내려가 화면에 "-4 / 8"처럼 보였습니다(운영 로그에 `attempts_page=-4`가 실제로 남아 있었음). 서버는 1페이지로 처리해서 데이터는 맞았지만 번호가 이상했습니다. 또 요청이 여러 개 동시에 나가면 **늦게 도착한 옛 응답이 최신 화면을 덮어쓸** 수 있었습니다.

## 바꾼 것

### A. 누르는 즉시 화면 반응

| 버튼 | 누른 순간 | 응답이 오면 |
|---|---|---|
| 페이지 "이전/다음" | 번호가 바로 바뀌고("3 / 8" → "4 / 8") 표가 흐려지며 "불러오는 중…" 표시 | 새 페이지를 그리고 흐림을 걷음 |
| 처리 버튼(해제·영구 해제·삭제·처리 완료·해결·승인·반려·회수·취소·회원가입 켜기/끄기·관리자 생성·영구 잠금 걸기, 17종) | "처리 중…"으로 바뀌고 다시 누를 수 없음 | 전체 갱신으로 결과를 반영. 실패·취소면 원래대로 |

- 페이지 번호는 누른 순간 **1과 마지막 페이지 사이**로만 움직인다(`goToPage`). 1페이지에서는 "이전" 버튼이 바로 사라진다.
- 처리 버튼은 **요청을 실제로 보내는 순간**에 "처리 중…"이 된다(`sendAction`). 그래서 확인 팝업이나 사유 입력을 취소하면 버튼은 그대로다.
- 처리 버튼은 처리 중에 다시 눌러도 요청이 한 번만 나간다(`runAction`). 더블 클릭으로 같은 요청이 두 번 나가지 않는다.
- 처리 결과는 지금처럼 **전체 갱신**으로 반영한다. 잠금 하나를 풀면 잠금 카드·보안 이벤트·영구 잠금 카드가 함께 바뀌기 때문이다.

### B. 필요한 표만 가져오기

`/api/status`에 선택 항목 `?only=<표 이름>`을 추가했습니다.

| 표 이름 | 표 |
|---|---|
| `attempts` | 최근 로그인 시도 |
| `users` | 회원 |
| `posts` / `comments` | 게시글 / 댓글 |
| `admin_log` | 관리자 로그인 기록 |
| `security_events` | 보안 이벤트 |
| `security_incidents` | 연관 사건 |
| `access_requests` | AI 조기 경보 |

- `only`가 있으면 **그 표의 이번 페이지와 전체 페이지 수만** 돌려준다. DB 조회는 세션 확인 1번 + 그 표 1번(로그인 시도 표는 위치 캐시 1번 더)이다.
- 만료된 잠금 정리는 하지 않는다(전체 갱신이 맡는다).
- 로그인 확인은 그대로다. 모르는 표 이름은 400으로 거절한다.
- `only`가 없으면 예전과 똑같이 동작한다(응답 형식 그대로).

**전체 갱신과 겹칠 때의 보호.** 5초마다 하는 전체 갱신이 출발한 뒤에 페이지를 넘기면, 늦게 도착한 전체 갱신이 그 표를 이전 페이지로 되돌려 놓을 수 있습니다. 그래서 표마다 "사용자가 페이지를 바꾼 횟수"(`sectionEpoch`)를 두고, 전체 갱신이 출발한 뒤 바뀐 표는 그 응답으로 그리지 않습니다. 또 같은 종류의 요청이 여러 개 나가면 **마지막 요청의 응답만** 그립니다(`latestStatusRequest`, `latestSectionRequest`).

### C. 전체 갱신 빠르게

| 변경 | 내용 |
|---|---|
| 한 번에 보내기 | 화면 데이터 조회와 "관리자 계정 관리" 카드의 권한 확인·목록까지 **17개를 한 번에** 보낸다(동시 처리 한도 = 조회 개수). 권한이 없으면 미리 받은 목록은 버리고 응답에 싣지 않는다 |
| 만료된 잠금 정리 간격 | 대시보드 갱신 때는 서버 인스턴스마다 **15초에 한 번만** 정리한다(`ADMIN_STATUS_RELEASE_INTERVAL_SECONDS`, 0이면 매번). 동시에 들어온 갱신 둘이 함께 정리하지 않게 잠금으로 보호한다 |

**감수할 점:** 만료된 잠금이 대시보드에 "잠김"으로 최대 15초 더 보일 수 있습니다. 실제 차단 해제는 `/login` 요청마다 따로 정리하므로 늦어지지 않습니다.

## 확인한 결과

**실제 대시보드 화면으로 검증.** 운영 관리자로 로그인하지 않고 확인하려고, Flask 테스트 클라이언트로 **실제 대시보드 템플릿**을 가짜 데이터와 함께 그렸습니다. 거기에 **실제 JS 파일**과 가짜 서버를 붙였습니다(전체 조회 1.5초, 표 하나 0.3초, 처리 0.4초 지연). 그런 다음 브라우저에서 눌러 봤습니다.

| 확인 | 결과 |
|---|---|
| "다음" 클릭 직후 | **3ms** 만에 "2 / 8" + "불러오는 중…" + 표 흐림 |
| 0.45초 뒤 | 2페이지 데이터, 흐림 해제. 요청은 `?only=attempts&attempts_page=2` 하나 |
| 2페이지에서 "이전" 6번 연타 | 즉시 "1 / 8"(1 아래로 안 내려감), 요청 1번 |
| "다음" 5번 연타 | 즉시 "6 / 8", 데이터도 6페이지(늦게 온 응답이 덮어쓰지 않음) |
| 전체 갱신 출발 직후 회원 표를 2페이지로 | 전체 응답(1페이지 기준)이 도착해도 **2페이지 유지** |
| "즉시 해제" 3번 연타 | 바로 "처리 중…"·비활성, `/api/unlock` 요청 **1번**, 끝나면 카드 사라짐 |
| 회원가입 토글 | 바로 "처리 중…", 끝나면 올바른 글자로 다시 누를 수 있음 |
| 확인 팝업 취소 | 버튼 그대로, 요청 없음 |
| 표 하나 요청 실패 | 흐림이 남지 않음 |
| 콘솔 오류 | 없음 |

**자동 테스트** — 667개 → **684개**, 전부 통과 (`tests/test_dashboard_speed.py` 17개 신규).

| 묶음 | 확인한 것 |
|---|---|
| `?only=` | 표 8종 각각 그 표만, 조회 1번, 다른 조회·정리 없음 / 로그인 시도 표는 위치 포함 / 모르는 표 400 / 로그인 없이 401 |
| 정리 간격 | 첫 갱신은 정리, 15초 안에는 건너뜀, 지나면 다시 정리 / 0이면 매번 |
| 한 번에 보내기 | 조회 17개 = 동시 처리 한도 17 / 권한이 없으면 관리자 목록을 싣지 않음 |
| 화면 연결 | 페이지 버튼 8개가 `goToPage`로, 처리 요청 17개가 모두 "처리 중" 표시를 거침, 옛 응답 무시 |

배포 후 운영 로그로 `/api/status`(전체)와 `?only=`(표 하나)의 처리 시간을 다시 재서 전후를 비교합니다.

## 🟠 HIGH

### 클릭재킹 / CSP — 모든 응답에 보안 헤더 붙이기

| 헤더 | 하는 일 |
|---|---|
| `X-Frame-Options: DENY` + CSP `frame-ancestors 'none'` | 이 사이트를 **다른 사이트의 `<iframe>`에 끼워 넣지 못하게** 함 (두 헤더를 함께 쓰는 이유: 앞은 옛 브라우저용, 뒤는 최신 표준) |
| CSP `script-src 'self'` 등 | 이 사이트가 직접 주지 않은 스크립트·스타일·이미지가 끼어드는 것을 막음 (폰트만 Google Fonts 예외) |
| `X-Content-Type-Options: nosniff` | 브라우저가 파일 내용만 보고 형식을 "추측"해 실행하는 것을 막음 |
| `Referrer-Policy` | 다른 사이트로 이동할 때 전체 주소가 넘어가는 것을 줄임 |

<aside>
🖱️ **클릭재킹(Clickjacking)이란?**
공격자가 내 사이트 화면을 **투명한 프레임**으로 자기 사이트 위에 몰래 겹쳐 놓고, 사용자가 "상품 받기" 버튼을 눌렀다고 믿는 순간 실제로는 **"즉시 해제"나 "회원 삭제"** 같은 버튼을 누르게 만드는 공격입니다. 파괴적 버튼이 있는 관리자 대시보드일수록 이 방어가 중요합니다.
</aside>

### 전역 HTTP 플러딩 방어 — 1분 120회
기존의 `*_RATE_LIMIT`(로그인·가입·글쓰기·댓글)은 **"특정 폼 제출"에만** 걸려 있어서 `/board`, `/dashboard` 같은 일반 페이지는 아무리 요청이 쏟아져도 다 받아줬습니다. 이제 **같은 IP가 1분에 120회**를 넘기면 **429**로 거절하고 `HTTP_FLOOD`(HIGH)로 기록합니다. 자동 폴링 API는 정상적으로도 자주 호출되므로 예외입니다.

## 🟡 MEDIUM

### 허니팟 — 사람 눈에 안 보이는 함정
화면에 **CSS로 숨겨둔 입력칸**(`website`)을 만들어 두면, 사람은 못 보니 **항상 비워 둡니다.** 폼의 모든 칸을 기계적으로 채우는 자동화 스크립트만 이 칸까지 채웁니다.

- 로그인·가입·글쓰기·댓글·회원 정보 변경 등 폼에서 재사용됩니다.
- 걸리면 **비밀번호 확인도, 시도 기록도 없이 즉시 거부**하고 `BOT_DETECTED`(MEDIUM)로만 남깁니다.
- 외부 CAPTCHA 서비스는 API 키 발급이 필요해서, **무료·의존성 없는** 이 방식을 선택했습니다.

### 타이밍 사이드채널 제거
| 상황 | 예전 | 지금 |
|---|---|---|
| 없는 아이디 | 해시 비교를 건너뛰고 **즉시** 실패 | **더미 해시**와 똑같이 비교한 뒤 실패 |
| 있는 아이디 + 틀린 비밀번호 | 해시 비교 후 실패 | 똑같음 |

비밀번호 비교는 일부러 **느리게** 설계되어 있어서, 예전에는 응답 시간 차이만으로 *"이 아이디는 존재하는구나"* 를 추측할 수 있었습니다. 더미 해시는 **서버가 켜질 때 딱 한 번** 만들어 둡니다(요청마다 만들면 그 계산 자체가 또 다른 시간차가 되기 때문). 관리자 로그인도 같은 원칙입니다.

### SSRF 입력 검증
서버가 외부 주소(`ip-api.com`)에 값을 끼워 요청하는 기능은, 그 값에 이상한 문자열이 들어오면 **요청 주소가 조작**될 수 있습니다. **진짜 IP(또는 IP 대역)** 일 때만 외부 요청을 보냅니다(4단원).

## 🟢 LOW

### 오픈 리다이렉트 수정
CSRF 토큰 오류가 나면 사용자를 **이전 화면(referrer)** 으로 돌려보냅니다. 그런데 referrer는 요청한 쪽이 **마음대로 정할 수 있는 값**이라, 검증 없이 따라가면 공격자 사이트로 링크를 걸어 "우리 사이트가 안내한 이동"처럼 보이게 악용할 수 있었습니다.

→ 이제 **이 사이트(`request.host`)로 돌아가는 주소일 때만** 보내고, 아니거나 없으면 **로그인 화면으로 고정**합니다.

## 🧪 예시로 보기

자동화 스크립트가 로그인 폼의 **모든 `<input>`을 기계적으로 채워 제출**(숨겨진 `website` 포함) → `is_bot_submission()`이 즉시 `True` → 자격 증명 확인·시도 기록 없이 곧바로 거부 + `BOT_DETECTED`(MEDIUM) 기록.

## 🖥️ 직접 해보기

- [ ] 브라우저 개발자 도구로 숨겨진 `website` 칸에 값을 채워 넣고 로그인 폼을 제출 → 일반 실패 문구와 함께 거부되는지 확인 (CSRF 토큰 없이 `curl`로 보내면 400이 먼저 뜨므로, 브라우저에서 시현)
- [ ] 개발자 도구 Network 탭의 응답 헤더에서 `X-Frame-Options: DENY`, `Content-Security-Policy`를 확인

## 📖 용어 사전

<details>
<summary><b>사이드채널(Side channel)</b></summary>

정상 응답의 "내용"이 아니라 **응답 시간 같은 부수적 정보**로 비밀을 추측하는 공격입니다.
</details>

<details>
<summary><b>SSRF</b></summary>

서버가 대신 외부에 요청을 보내는 기능을 악용해, 의도하지 않은 주소로 요청을 보내게 만드는 공격입니다.
</details>

<details>
<summary><b>오픈 리다이렉트</b></summary>

"이 주소로 이동시켜 줘"라는 기능이 **검증 없이 아무 주소나** 받아들여, 공격자 사이트로 사용자를 보내는 데 쓰이는 약점입니다.
</details>

## ⚠️ 알아둘 한계

- 전역 요청 한도는 **메모리 기반**이라, 서버 인스턴스가 여러 개(예: Vercel 서버리스 다중 인스턴스)면 **카운트가 공유되지 않을 수 있습니다.**
- 프롬프트 인젝션처럼 100% 막을 수 없는 유형은 사람의 승인 단계로 보완합니다(11단원).

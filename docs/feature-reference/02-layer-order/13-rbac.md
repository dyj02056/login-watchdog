# 13. 관리자 RBAC

<aside>
🎯 **한 줄 요약**
"로그인만 되면 뭐든 할 수 있다"는 위험합니다. **역할(Role)별로 할 수 있는 일을 나눠**, 조회 담당자 계정이 털려도 회원 삭제나 관리자 계정 생성까지는 못 하게 **피해 범위를 제한**합니다.
</aside>

## 🏢 비유로 먼저 이해하기

| 현실 | 이 프로젝트 |
|---|---|
| 회사 **출입증 등급** (방문자 / 일반 직원 / 임원) | 역할 (`security_viewer` / `security_admin` / `super_admin`) |
| 등급별로 열리는 문이 다름 | 역할별 허용 액션 (`permissions` 표) |
| 문 앞에서 **카드를 매번 찍음** | 요청마다 DB로 권한 확인 |

<aside>
💡 **RBAC란?** Role-Based Access Control. **사람이 아니라 "역할"에 권한을 주고**, 사람은 역할에 배정되는 접근 제어 방식입니다.
</aside>

---

## 👥 역할과 권한

| 역할 | 할 수 있는 일 |
|---|---|
| `security_viewer` | **조회만** |
| `security_admin` | 조회 + **잠금 해제 · 이벤트 처리 · 사건 해결** |
| `super_admin` | **전부** (회원 삭제, 관리자 계정 관리 포함) |

| 액션 | viewer | security_admin | super_admin |
|---|:-:|:-:|:-:|
| `unlock_ip` (잠금 해제) | ❌ | ✅ | ✅ |
| `resolve_security_event` | ❌ | ✅ | ✅ |
| `resolve_incident` | ❌ | ✅ | ✅ |
| `delete_user` | ❌ | ❌ | ✅ |
| `manage_admin_users` | ❌ | ❌ | ✅ |

> 실제 매핑은 DB의 `permissions` 표에 저장되어 있습니다.

---

## 🚧 권한 문지기 — 두 단계로 확인

라우트 위에 `@require_permission("unlock_ip")`처럼 **필요한 액션**을 적어 둡니다.

| 순서 | 확인 | 통과 못 하면 |
|:-:|---|---|
| ① | **세션이 아직 유효한 관리자인가?** (매 요청마다 DB 확인) | 401 / 다시 로그인 |
| ② | **이 역할이 이 액션을 해도 되나?** | **403** "이 작업을 수행할 권한이 없습니다." |
| ③ | 통과 → 실제 처리 함수 실행 | |

<aside>
🎯 **처리 함수는 권한을 다시 확인하지 않습니다.**
"요청한 사람이 진짜 관리자인가"는 문지기가 **이미 끝낸 뒤**에만 처리 함수가 호출되기 때문입니다. 확인을 한 곳에 모아 두면 빠뜨릴 일이 줄어듭니다.
</aside>

---

## ⏱️ 권한은 캐싱하지 않습니다 (즉시 회수)

권한을 메모리에 담아 두면, super_admin이 다른 관리자의 권한을 방금 바꿨는데도 **그 관리자가 로그아웃하기 전까지 예전 권한이 유지**됩니다. 그래서 **요청마다 DB를 직접 조회**합니다. 권한 회수가 **재로그인 없이 즉시** 반영됩니다.

<aside>
👀 **화면용 권한 목록은 "표시용"일 뿐입니다.**
대시보드는 "이 관리자에게 어떤 버튼을 보여줄지" 정하려고 권한 목록을 받지만, **실제 검사는 서버가 요청마다** 따로 합니다. 버튼을 억지로 눌러도 서버가 막습니다.
</aside>

---

## 🔒 super_admin은 이 화면에서 만들 수 없습니다

"super_admin은 1명만 둔다"는 운영 정책을 **코드로 강제**합니다.

| 방어 | 설명 |
|---|---|
| 만들 수 있는 역할 제한 | `("security_viewer", "security_admin")` — **super_admin이 목록에 없음** |
| 삭제 전 역할 확인 | 대상이 super_admin이면 거부 (안 막으면 마지막 super_admin까지 지워질 수 있음) |
| 화면 + 서버 양쪽 | 화면(select 옵션)에서도 안 보이지만, `fetch()`를 직접 조작한 요청까지 **서버가 다시 막음** |

---

## 📍 코드는 어디에 있나요?

| 하는 일 | 파일 | 함수 |
|---|---|---|
| 권한 문지기 | `helpers/auth.py` | `require_permission()`, `_load_current_admin()` |
| 권한 조회 (캐싱 없음) | `db/roles.py` | `has_permission()`, `list_role_permissions()` |
| 관리자 계정 생성·삭제 | `routes/admin/manage.py` | `api_admin_users_create()`, `api_admin_users_delete()` |
| 계정 저장·조회 | `db/admin.py` | `create_admin_user()`, `get_admin_role_by_id()`, `delete_admin_user()` |

## 🖥️ 직접 해보기

- [ ] super_admin으로 로그인 → "관리자 계정 관리"에서 `security_viewer` 계정을 만든다
- [ ] 그 계정으로 로그인 → "즉시 해제"를 눌러 **403**(권한 없음)이 나오는지 확인한다
- [ ] (DB에서 역할을 바꾼 뒤) **재로그인 없이** 같은 세션에서 다시 "즉시 해제"가 되는지 확인한다

> 참고: 개발자 도구 Network 탭에서 403 응답을 볼 수 있습니다.

---

## ⚠️ 알아둘 한계

- **역할 자체를 바꾸는 화면(API)은 이 저장소에서 확인되지 않았습니다.** 권한 표는 운영 중 DB에서 직접 바꾸는 방식으로 보이며, 대시보드에는 권한 편집 화면이 없습니다.

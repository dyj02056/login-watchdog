## 🏢 비유로 먼저 이해하기

| 현실 | 이 프로젝트 |
|---|---|
| 건물 안내 데스크가 **"그런 분은 안 계십니다"** vs **"지금 외출 중이십니다"** 라고 다르게 답함 → 입주자 여부가 새어 나감 | 응답 차이로 가입 여부가 드러남 |
| 안내 데스크가 **항상 "확인해 보겠습니다"** 로만 답함 | 항상 같은 문구 |

📚 **계정 열거(Enumeration)란?** 응답의 차이로 **가입된 아이디 목록을 알아내는** 공격입니다.
</aside>

## 🔍 새고 있던 두 가지와 막은 방법

| 새던 곳 | 왜 새나 | 해결 |
|---|---|---|
| 로그인 화면의 **"영구 잠금"** 문구 | 영구 승격은 **가입된 아이디에만** 일어남 → "영구 잠금"이라고 알려주면 가입 사실이 드러남 | 임시든 영구든 **같은 문구 + 같은 복구 링크** |
| 6자리 코드 화면의 **"남은 시도 N회"** | 진행 중인 복구가 있다 = 가입된 아이디 | 요청한 기기가 **아니면 모두 같은 문구**, 시도권도 쓰지 않음 |
| 아이디로 복구 요청을 찾는 **조회 시간** | "회원 조회 → 요청 조회" 두 번 왕복 → 있는 아이디는 한 번 더 걸림 | **inner join 한 번**으로 어느 쪽이든 같은 시간 |

## 🔄 동작 순서

### 1) 계정 잠금 안내 — 한 문구로
```
"잠긴 계정입니다. 잠시 후 다시 시도해주세요. 계속 로그인할 수 없다면 아래 '본인 인증으로 잠금 해제'를 이용하거나 관리자에게 문의해주세요."
```
- **임시 잠금도, 영구 잠금도 똑같이** 이 문구를 씁니다.
- **복구 링크도 항상 같이** 보여줍니다. (링크를 영구 잠금에만 보여주면 링크 유무로 다시 구분되기 때문)

### 2) 6자리 코드는 "요청한 기기"에서만

| 순서 | 동작 |
|:-:|---|
| ① | 아이디로 복구 요청을 **inner join 한 번**에 찾음 |
| ② | **요청 없음 · 아이디 없음 · 다른 기기**는 모두 **같은 문구** (시도권도 사용 안 함) |

→ 다른 기기에서는 ① 이 아이디에 복구가 진행 중인지 **알 수 없고**, ② 틀린 코드를 넣어 **남의 복구 요청을 취소시킬 수도 없습니다.**

## 📍 코드는 어디에 있나요?

| 하는 일 | 파일 | 함수·상수 |
|---|---|---|
| 잠금 안내 문구 통일 | `routes/auth.py` | `ACCOUNT_LOCKED_MESSAGE`, `login_submit()` |
| 복구 링크 표시 | `routes/auth.py` | `_login_form()` |
| 코드는 요청한 기기에서만 | `routes/recovery.py` | `recovery_verify_submit()`, `_device_matches()` |
| 공통 실패 문구 | `routes/recovery.py` | `CODE_GENERIC_FAILURE_MESSAGE` |
| 아이디로 요청 한 번에 찾기 | `db/recovery.py` | `get_latest_pending_recovery_for_username()` |

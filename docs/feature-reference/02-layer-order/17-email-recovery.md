# 17. 이메일 인증 복구

<aside>
🎯 **한 줄 요약**
영구 잠금을 관리자만 풀 수 있으면 억울하게 잠긴 사용자는 기다리기만 해야 합니다. **본인 이메일로 인증하면 스스로 풀 수 있게** 하되, **누가 가입자인지 새어 나가지 않게**, 그리고 **공격자가 이 길을 악용하지 못하게** 여러 겹으로 막았습니다.
</aside>

> 📚 **계층**: Layer 5-A. 확장 기능 — Layer 1에 새 화면(`/recovery`)이 생기고, 영구 잠금을 **본인 인증**으로 되돌리는 경로

---

## 🏢 비유로 먼저 이해하기

| 현실 | 이 프로젝트 |
|---|---|
| 출입 금지된 직원이 **등록된 연락처로 본인 확인** 후 복귀 | 가입 이메일로 링크·코드 발송 |
| 아파트는 **세대원 한 명 + 그 기기**만 통과시키는 **임시 출입증** (IP는 여러 사람이 같이 쓰므로) | IP 복구 = "회원 + 기기" 예외 발급 |
| 복귀 직후 한동안 **관찰 기간** | 24시간 보호관찰 |

---

## ✉️ 복구 방식은 두 가지

| 잠긴 대상 | 인증하면 | 이유 |
|---|---|---|
| **계정** 영구 잠금 | **완전 해제** + **24시간 보호관찰** (그 안에 다시 잠기면 관리자 전용) | 계정은 본인 한 명의 것 |
| **IP** 영구 잠금 | IP는 **잠긴 채로 두고**, "그 회원 + 요청한 기기"에게만 **30일 예외(출입증)** | IP는 여러 사람이 함께 쓸 수 있음 |

---

## 🔄 1) 복구 메일 요청

| 순서 | 동작 | 쉬운 설명 |
|:-:|---|---|
| ① | **기기 쿠키** 발급 | 복구를 요청한 브라우저를 구분하는 무작위 쿠키 |
| ② | 봇이면 같은 문구로 종료 | 허니팟(15단원) |
| ③ | **응답 시간을 5초로 고정** | 빨리 끝나든 오래 걸리든 응답 시점이 같음 |
| ④ | IP당 **시간당 한도** | 넘기면 다른 문구로 거절 (IP 기준이라 존재 여부와 무관) |
| ⑤ | 하루 한도 · **60초 쿨다운** · 잠금 상태 조회 | 3개를 **동시에** 조회 |
| ⑥ | 풀 수 있는 대상인지 결정 | 대상이 없으면 **메일 없이 조용히** 끝 |
| ⑦ | 링크 토큰 + **6자리 코드** 생성, **해시만 저장** | 원문은 메일에만 존재 |
| ⑧ | **메일 발송** | 실패하면 요청을 취소 |

### 🕵️ 계정이 있는지 알아낼 수 없게 하는 장치들

| 장치 | 설명 |
|---|---|
| **항상 같은 문구** | "등록된 이메일이 있다면 안내 메일을 보냈습니다." — 아이디가 없든, 잠기지 않았든 똑같이 |
| **응답 시간 5초 고정** | 아이디가 없으면 DB 한두 번으로 끝나고, 실제 메일은 조회 여러 번 + 메일 서버까지 거치므로 그냥 두면 **시간 차이로 존재가 드러남** |
| **처리 중 예외도 삼킴** | 예외가 500으로 새면 "이 아이디는 처리 중 오류가 났다"는 신호가 됨 |
| **메일은 응답 전에 발송** | 서버리스(Vercel)는 응답을 보내면 함수를 멈추므로, 백그라운드로 미루면 메일이 끊길 수 있음 |

## 🔗 2) 링크·코드로 복구 완료

| 순서 | 동작 | 쉬운 설명 |
|:-:|---|---|
| 링크 열기 | **GET**은 확인 화면만 | 메일 보안 스캐너가 링크를 먼저 열어도 **토큰이 닳지 않음** |
| ① | 확인 버튼 **(POST)** | IP 복구는 **요청한 기기**에서만 완료됨 |
| ② | 6자리 코드 경로 | 비교하기 **전에** 시도권부터 예약 (20단원) |
| ③ | **1회만 소비** | PENDING → VERIFIED (조건부 UPDATE) |
| ④ | 실제 조치 반영 | 계정 해제+보호관찰 / IP 예외 발급 |
| ⑤ | 완료 안내 메일 | 이메일 인증으로도 인정 (23단원) |

<aside>
🔐 **IP 복구가 "요청한 기기에서만" 되는 이유**
공격자가 **피해자의 아이디로 복구를 요청**하고, 피해자가 메일의 링크를 눌러도, **예외는 공격자 기기에는 발급되지 않습니다.** 예외는 "복구를 요청한 기기"의 해시와 맞아야만 발급되기 때문입니다.
</aside>

---

## 🪪 3) 예외로 로그인하기

영구 잠긴 IP에서는 **회원 + 기기 쿠키가 모두 맞는** 사람만 로그인 절차로 들어갑니다. 같은 IP의 다른 기기는 계속 차단됩니다.
예외로 들어온 회원이 **연달아 틀리면 예외가 회수**됩니다. 예외는 "본인이 비밀번호를 아는 상황"을 전제로 한 출입증이라, 계속 틀리면 도용 신호로 보기 때문입니다.

## 🧪 예시로 보기

`wdprod01`이 영구 잠긴 IP에서 복구를 요청 → `recovery_requests`에 `target_kind=ip`, `status=PENDING`, `token_hash`·`code_hash`·`device_hash`(모두 **해시**) → 같은 기기에서 코드 입력 → `VERIFIED` → `ip_lock_exemptions`에 `ACTIVE`, 30일 만료로 한 줄 추가.
→ 이 회원은 **그 기기로만** 로그인할 수 있고, 같은 IP의 다른 기기는 계속 차단됩니다.

## 🖥️ 직접 해보기

- [ ] 개발 환경: `docker compose -f docker-compose.mailpit.yml up -d` + `.env`에 `MAIL_BACKEND=smtp`, `SMTP_HOST=127.0.0.1`, `SMTP_PORT=1025`, `SMTP_STARTTLS=false`
- [ ] 16단원의 방법으로 영구 잠금을 만든 뒤, 로그인 화면의 **"본인 인증으로 잠금 해제"**에서 아이디를 입력
- [ ] http://127.0.0.1:8025 에서 메일을 확인하고, **같은 브라우저**에서 링크를 열어 [해제]
- [ ] **다른 브라우저**(쿠키 없음)에서 같은 링크를 열면 "요청한 기기에서만" 안내가 뜨는지 확인
- [ ] 배포 환경의 메일 설정 확인: `python scripts/management/send_test_mail.py --to 주소`

## 📖 용어 사전

<details>
<summary><b>토큰·코드를 "해시로만 저장"</b></summary>

원문은 메일에만 있고 DB에는 SHA-256 **지문**만 남습니다. DB가 유출돼도 복구 링크를 만들 수 없습니다.
</details>

<details>
<summary><b>기기 쿠키(`lw_dev`)</b></summary>

복구를 요청한 브라우저를 구분하는 무작위 쿠키입니다. 자바스크립트로 못 읽게(HttpOnly), 운영 환경에서는 HTTPS에서만(Secure) 전송합니다.
</details>

<details>
<summary><b>보호관찰</b></summary>

복구 직후 24시간 동안, 그 안에 다시 잠기면 **관리자만** 풀 수 있게 하는 기간입니다.
</details>

<details>
<summary><b>메일 발송 실패 알림</b></summary>

사용자 화면은 항상 같은 안내라서, 메일 설정이 틀려도 아무도 모를 수 있습니다. 그래서 실패 원인을 `CONFIG / AUTH / CONNECT / OTHER / INTERNAL`로 나눠 Slack으로 알리고, 같은 원인은 **1시간에 한 번만** 보냅니다.
</details>

## ⚠️ 알아둘 한계

- 가입할 때 이메일 소유 확인이 없어서, **오타 주소로 가입했다면 메일을 받을 수 없습니다.** (이후 23단원의 이메일 인증으로 보완)
- Gmail처럼 **나중에 반송**하는 경우는 "존재하지 않는 이메일"로 감지하지 못합니다.

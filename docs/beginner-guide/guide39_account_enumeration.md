# 39단계 — 로그인·복구 응답으로 계정 존재 여부가 드러나지 않게

[◀ 38단계](guide38_admin_account_lockout.md) · [전체 목차](beginner-guide.md) · [40단계 ▶](guide40_email_verification.md)

> [34단계](guide34a_email_recovery.md)의 복구 요청 화면은 계정이 있는지 철저히 숨겼지만, 정작 **로그인 화면의 잠금 문구**와 **6자리 코드 입력 화면**이 가입 여부를 알려주고 있었습니다. 두 곳을 막고, 그 과정에서 찾은 **"남의 복구 요청을 취소시키는 공격"**도 함께 막았습니다. DB 스키마는 바뀌지 않습니다.

## 계정 존재 여부 탐색(enumeration)이란

공격자가 아이디 목록을 넣어 보면서 응답 차이로 **어떤 아이디가 실제로 가입되어 있는지** 알아내는 것입니다. 가입된 아이디만 골라내면 비밀번호 대입이나 피싱을 훨씬 효율적으로 할 수 있습니다. 응답 문구뿐 아니라 화면 요소(링크 유무), 응답 시간 차이도 단서가 됩니다.

## 1. 로그인 화면: "영구 잠금된 계정입니다"

### 무엇이 문제였나

| 잠금 | 없는 아이디에도 걸리나 | 기존 문구 |
|---|---|---|
| 임시 계정 잠금 | ✅ 실패 기록만으로 잠김 | "잠긴 계정입니다. 잠시 후 다시 시도해주세요." |
| 영구 계정 잠금 | ❌ **가입된 아이디만** 승격(`lockdown.promote_account`) | "**영구 잠금**된 계정입니다…" + 복구 링크 |

임시 잠금 문구는 아무것도 알려주지 않지만, "영구"라는 단어와 복구 링크가 보이면 **그 아이디는 가입되어 있다**는 뜻이었습니다. 공격자는 같은 아이디로 반복해서 실패해 승격을 유도한 뒤 이 문구로 확인할 수 있었습니다.

### 바꾼 것

계정이 잠겼으면 **임시든 영구든 완전히 같은 화면**을 보여줍니다.

> 잠긴 계정입니다. 잠시 후 다시 시도해주세요. 계속 로그인할 수 없다면 아래 '본인 인증으로 잠금 해제'를 이용하거나 관리자에게 문의해주세요.

복구 링크도 **모든 계정 잠금에** 보여줍니다 — 영구 잠금에만 보여주면 링크 유무로 다시 구분되기 때문입니다. 임시 잠금 사용자가 링크를 눌러도 복구 화면은 원래 항상 같은 응답을 주고 메일은 보내지 않으므로 문제가 없고, 복구 화면 안내에 "몇 분 뒤 자동으로 풀리는 잠금이라면 메일이 가지 않으니 잠시 후 다시 로그인해 보세요"를 추가했습니다.

IP 잠금 문구("이 네트워크는 차단되어 있습니다")는 그대로입니다. IP 상태에 대한 안내라 아이디 가입 여부와 무관합니다.

**사용성 손해:** 영구 잠금된 본인도 "잠시 후 다시 시도"를 보게 됩니다. 같은 화면의 "계속 안 되면 본인 인증" 안내로 넘어가면 됩니다.

## 2. 6자리 코드 화면: "남은 시도 N회"

### 무엇이 문제였나

| 입력 | 기존 응답 |
|---|---|
| 없는 아이디, 또는 진행 중인 복구가 없는 아이디 | "아이디 또는 코드가 올바르지 않거나 만료되었습니다." |
| 진행 중인 **IP 복구**가 있는 아이디 + 다른 기기 | "요청한 기기에서만…" ← 드러남 |
| 진행 중인 **계정 복구**가 있는 아이디 | "코드가 올바르지 않습니다 (남은 시도 4회)" ← 드러남 |

더 나쁜 점도 있었습니다. 계정 복구 코드는 **아이디만 알면 어느 기기에서나** 넣을 수 있어서, 공격자가 피해자 아이디로 틀린 코드를 5번 넣으면 [37단계](guide37_session_and_code_hardening.md)의 시도 제한 때문에 **피해자의 복구 요청이 취소**됐습니다. 영구 잠금된 피해자가 스스로 풀지 못하게 계속 방해할 수 있었던 셈입니다.

### 바꾼 것

코드 입력을 복구 종류와 무관하게 **"복구를 요청한 기기"(`lw_dev` 쿠키)에서만** 받습니다. IP 복구는 원래 그랬고, 이제 계정 복구도 같습니다. 모든 복구 요청에 이미 기기 해시가 저장되어 있어서 스키마 변경은 없고, 복구 메일도 원래 "복구를 요청하신 기기의 화면에서 코드를 입력하세요"라고 안내하고 있었습니다.

```
아이디 없음 ─┐
요청 없음 ───┼─→ "아이디 또는 코드가 올바르지 않거나 만료되었습니다."  (시도권 사용 안 함)
다른 기기 ───┘
요청한 기기 ──→ 시도권 예약 → 코드 비교 → "남은 시도 N회" 또는 완료
```

- 다른 기기에서는 이 아이디에 복구가 진행 중인지 **알 수 없고**, 틀린 코드를 넣어도 **시도권이 줄지 않아** 남의 복구를 취소시킬 수 없습니다.
- "남은 시도 N회"는 요청한 기기에서만 보입니다 — 그 사람은 자기가 복구를 요청했다는 걸 이미 압니다.
- **메일의 링크는 그대로 어느 기기에서나 동작합니다**(계정 복구). 링크에는 추측할 수 없는 토큰이 들어 있어서 링크를 가진 사람은 메일 주인입니다.

**사용성 손해:** PC에서 요청하고 휴대폰 브라우저에 코드를 넣는 경우는 실패합니다. 이때는 휴대폰에서 메일 링크를 누르면 됩니다.

### 응답 시간 차이도 없앴다

예전에는 "아이디로 회원 조회 → 있으면 그 id로 복구 요청 조회"였습니다. **없는 아이디는 DB 왕복 1번, 있는 아이디는 2번**이라 원격 Supabase에서는 0.2~0.5초 차이가 났고, 여러 번 재 보면 가입 여부를 추측할 수 있었습니다. 이제는 `users`와 inner join한 **한 번의 조회**로 찾습니다.

```python
# db/recovery.py — get_latest_pending_recovery_for_username()
.select("*, users!inner(username)")
.eq("users.username", username)
.eq("status", "PENDING")
```

## 남은 위험

- **회원가입**의 "이미 사용 중인 아이디 또는 이메일입니다"도 가입 여부를 알려줍니다. 이걸 숨기려면 가입 확인 메일(이메일 소유 확인)로 가입 흐름을 바꿔야 해서 별도 작업으로 남겼습니다. 가입은 IP당 빈도 제한(`SIGNUP_RATE_LIMIT`)이 있어 대량 확인은 어렵습니다.
- 관리자 로그인은 [38단계](guide38_admin_account_lockout.md)에서 "없는 아이디도 똑같이 잠금 + 같은 문구"로 이미 처리했습니다.

# 41단계 — 비밀번호 찾기 (인증된 이메일로 재설정)

[◀ 40단계](guide40_email_verification.md) · [전체 목차](beginner-guide.md) · [42단계 ▶](guide42_ipv6_prefix.md)

> 지금까지 비밀번호를 잊은 회원은 스스로 해결할 방법이 없어 관리자가 처리해야 했습니다. [40단계](guide40_email_verification.md)에서 "확인된 이메일"과 "세션만으로는 바꿀 수 없는 이메일"을 만들어 두었으므로, 이제 그 이메일로 **비밀번호를 재설정**할 수 있게 했습니다. DB 스키마 변경은 없습니다(토큰 용도 `PASSWORD_RESET`은 40단계 마이그레이션에서 미리 정의).

## 흐름

```
/login "비밀번호 찾기"  (또는 프로필의 "이메일로 재설정" — 아이디가 미리 채워짐)
 → /password/forgot: 아이디 입력
 → 항상 같은 안내 + 고정 응답 시간
   "인증된 이메일이 등록된 계정이라면 비밀번호 재설정 메일을 보냈습니다"
 → [인증된(VERIFIED) 계정만] 재설정 링크 메일 (15분, 1회용)
 → 링크 → 새 비밀번호 입력 화면 (토큰은 아직 소비 안 함)
 → [비밀번호 재설정] → 형식 검사 통과 시에만 토큰 소비 + 비밀번호 변경
 → 모든 기기 로그아웃 + "비밀번호가 재설정되었습니다" 알림 메일 → 로그인 화면
```

## 왜 인증된 이메일에만 보내나

재설정 메일은 **계정을 통째로 되찾는 메일**입니다. 확인된 적 없는 주소(오타, 남의 주소)로 보내면 엉뚱한 사람이 계정을 가져갈 수 있습니다. 그래서:

| 이메일 상태 | 재설정 메일 |
|---|---|
| `VERIFIED` | 보냄 |
| `UNKNOWN`(미인증, 기존 회원 포함) | 보내지 않음 — 로그인한 상태에서 먼저 인증해야 함 |
| `UNDELIVERABLE`(반송) | 보내지 않음 |

이메일이 세션만으로 바뀌지 않게 막은 것도 40단계입니다. 그 보호가 없었다면 "세션 탈취 → 이메일 변경 → 재설정 → 계정 탈취"가 가능했습니다.

## 계정 존재 여부를 드러내지 않는다

| 입력 | 화면 응답 | 실제 |
|---|---|---|
| 인증된 계정 | 같은 안내 | 메일 발송 |
| 미인증·반송 계정 | 같은 안내 | 메일 없음 |
| 없는 아이디 | 같은 안내 | 메일 없음 |
| 회원별 하루 한도(3회)·쿨다운(60초) 초과 | 같은 안내 | 메일 없음 |
| 같은 IP가 1시간에 5회 초과 | "요청이 너무 많습니다" | IP 기준이라 가입 여부와 무관 |

응답 시간도 [34단계](guide34a_email_recovery.md) 복구 요청과 같은 **고정 응답 시간**(`RECOVERY_MIN_RESPONSE_SECONDS`, 기본 8초 → [43단계](guide43_recovery_request_limit.md)에서 5초)으로 맞춥니다. 메일을 보내는 경우와 아무것도 안 하는 경우의 처리 시간 차이로 가입 여부를 추측할 수 없게 하기 위해서입니다. 복구 화면의 함수(`run_with_fixed_response_time`)를 그대로 공용으로 씁니다.

## 링크 처리의 세부 원칙

| 원칙 | 구현 |
|---|---|
| 메일 보안 스캐너가 미리 열어도 안 닳게 | 링크(GET)는 입력 화면만, 소비는 [비밀번호 재설정] POST에서만 |
| **입력 실수로 링크가 닳지 않게** | 새 비밀번호 길이·확인 일치를 **먼저** 검사하고, 통과해야 토큰을 소비 |
| 같은 링크로 두 번 바꾸지 못하게 | 조건부 UPDATE로 1회 소비 |
| 이메일을 바꾼 뒤 옛 주소로 간 링크 | 토큰에 저장된 주소와 지금 이메일이 다르면 무효 |
| 용도 섞임 방지 | 재설정 토큰은 `/email/confirm`에서, 인증 토큰은 `/password/reset`에서 **거절**(소비도 안 함) |
| 무차별 대입 | 32바이트 무작위 토큰 + 두 POST에 IP당 분당 10회(`PASSWORD_RESET_RATE_LIMIT_PER_MINUTE`) |
| 6자리 코드는? | **쓰지 않음.** 링크를 가진 사람이 곧 메일함 주인이라 기기 제한이 필요 없고, 코드 대입이라는 공격 면을 아예 만들지 않는다 |

재설정은 [35단계](guide35_password_change.md)의 `db.update_user_password()`를 그대로 써서 **세션 세대 번호(`session_version`)가 올라갑니다** — 탈취된 세션을 포함해 모든 기기의 로그인이 끊깁니다. 재설정은 **잠금을 풀지 않습니다**(영구 잠금은 34단계 복구로 따로 풉니다).

## 구현 중 막은 빈틈

40단계의 `/email/confirm`은 토큰을 찾으면 용도와 관계없이 소비한 뒤 용도를 확인했습니다. 재설정 토큰이 생기면서, 재설정 링크의 토큰을 `/email/confirm`에 넣으면 **재설정 링크가 닳아 버리는** 문제가 생길 수 있었습니다. 이제 `/email/confirm`은 이메일 인증·변경 토큰만 찾고(`get_pending_email_token`), 재설정 토큰은 소비하지 않고 무효로 답합니다.

## 로컬에서 확인한 실제 흐름

`MAIL_BACKEND=console`로 띄운 로컬 서버 + 운영 Supabase, 40단계에서 인증해 둔 테스트 회원으로 확인했습니다.

1. 프로필의 "이메일로 재설정" → 아이디가 미리 채워진 비밀번호 찾기 화면
2. 요청 → 같은 안내, 인증된(변경 후) 주소로 재설정 링크 출력
3. 링크 → 새 비밀번호 화면 → 7자 비밀번호 → "최소 8자 이상" (링크는 그대로)
4. 올바른 비밀번호 → 로그인 화면 + "비밀번호가 재설정되었습니다", **같은 브라우저에 남아 있던 이전 로그인도 해제**
5. 같은 링크 재사용 → "만료되었거나 이미 사용된 링크"
6. 이전 비밀번호 로그인 실패, 새 비밀번호 로그인 성공 / 재설정 알림 메일 출력 / 서버 오류 없음

## 확인한 결과 (자동 테스트)

600개 → **625개**, 전부 통과 (`tests/test_password_reset.py` 25개 신규).

| 묶음 | 확인한 것 |
|---|---|
| 요청 | 인증된 계정만 링크(해시만 저장) / 없는 아이디·미인증·반송·형식 오류는 메일 없음 / 회원별 하루 한도 / 수신 거부면 반송 표시 |
| 화면 | 인증·미인증·없는 아이디의 응답이 같음 / IP 한도 / 허니팟 / 아이디 미리 채우기(형식이 맞을 때만) / 11번째 요청은 429 |
| 재설정 | GET은 소비 안 함 / 짧거나 불일치한 비밀번호는 링크를 닳게 하지 않음 / 성공 시 비밀번호 변경·알림·다른 기기 로그아웃 / 재사용 불가 / 이메일이 바뀐 뒤의 옛 링크 무효 |
| 용도 분리 | 재설정 토큰은 `/email/confirm`에서 거절·미소비, 인증 토큰은 `/password/reset`에서 거절 |
| 연결 | 로그인 화면 링크 / 프로필: 인증됨이면 재설정 링크, 미인증이면 인증 먼저 안내 |

## 운영상 알아둘 점

- **기존 회원은 이메일을 먼저 인증해야** 이 기능을 쓸 수 있습니다. 이미 비밀번호를 잊은 미인증 회원은 지금처럼 관리자가 처리합니다.
- 로그인 화면은 관리자 로그인과 같은 템플릿이라 `/admin/login`에도 "비밀번호 찾기" 링크가 보입니다(회원가입 링크와 같은 기존 방식 — 두 로그인 화면을 겉보기로 구분하지 않는다). 이 기능은 **회원 계정에만** 동작하며, 관리자 비밀번호 재설정은 범위 밖입니다.

# 45단계 — 보이지 않는 탭은 폴링하지 않는다

[◀ 44단계](guide44_log_retention.md) · [전체 목차](beginner-guide.md)

> 관리자 대시보드는 5초마다 `/api/status`를 호출하고, 그 요청 한 번에 DB 조회가 약 21번 일어납니다. 그런데 이 호출은 **탭이 안 보여도** 계속됐습니다. 관리자 탭을 켜 둔 채 다른 일을 하면 분당 약 250번씩 DB를 왕복한 셈입니다. 이제 탭이 숨겨지면 멈추고, 다시 보이면 즉시 갱신합니다. 게시글 화면의 새 댓글 확인도 같은 방식으로 바꿨습니다. DB 스키마 변경은 없습니다.

## 문제

| 화면 | 이전 방식 | 문제 |
|---|---|---|
| 관리자 대시보드 (`dashboard/main.js`) | `setInterval(fetchStatus, 5000)` | 숨겨진 탭에서도 5초마다 DB 조회 약 21번 → 분당 약 250번, 하룻밤이면 약 36만 번 |
| 게시글 화면 (`board.js`) | `setInterval(checkForNewComments, 5000)` | 회원 누구나 여는 화면이라, 열어 둔 탭마다 계속 확인 |
| 두 화면 공통 | `setInterval`은 이전 요청이 끝났는지 보지 않음 | 서버가 주기(5초)보다 느리면 요청이 겹쳐 쌓임 |

`/api/status` 한 번의 DB 조회:

| 순서 | 내용 | 조회 수 |
|---|---|---|
| ① | 세션 확인(관리자 계정 조회, 37단계) | 1 |
| ② | 만료된 잠금 정리 3종(IP·회원 계정·관리자 계정) | 3 이상 |
| ③ | 대시보드 표·카드 데이터(동시에) | 16 |
| ④ | 로그인 기록의 위치 캐시 | 1 |

## 바꾼 것

### 1. 공용 폴링 부품 `public/js/polling.js`

`startPolling(작업, 주기, { immediate })` 하나를 두 화면이 같이 씁니다.

| 규칙 | 동작 |
|---|---|
| 탭이 숨겨지면 | 예약된 다음 요청을 취소하고 멈춘다(브라우저의 `document.hidden` / `visibilitychange`) |
| 탭이 다시 보이면 | 다음 주기를 기다리지 않고 **즉시 한 번** 갱신한 뒤 주기를 재개한다 |
| 다음 요청 시점 | **응답을 받은 뒤** 주기만큼 기다렸다가(setTimeout 연쇄) — 한 화면에서 진행 중인 요청은 항상 하나 |
| 작업이 실패하면 | 콘솔에 남기고 계속 폴링한다(일시적 오류 한 번으로 화면이 멈추지 않게) |
| `immediate` | 대시보드는 열자마자 한 번 가져오고(true), 게시글 화면은 서버가 방금 최신 상태로 그렸으므로 한 주기 뒤부터 확인한다(false) |

- `dashboard/main.js`: `setInterval` 대신 `startPolling(fetchStatus, pollIntervalMs)`
- `dashboard/api.js`: 페이지 번호를 바로잡은 뒤 다시 가져오는 호출을 `await fetchStatus()`로 바꿔, 그 재요청까지 끝나야 다음 주기가 예약되게 했다
- `board.js`: `startPolling(checkForNewComments, …, { immediate: false })`. `import`를 쓰므로 `board_detail.html`에서 `type="module"`로 불러온다

### 2. 서버: 만료된 잠금 정리 3종을 동시에

`/api/status`의 ②를 차례대로 하던 것을 동시에 돌립니다. 조회 수는 같지만 원격 DB 왕복 대기가 겹쳐져 응답이 빨라집니다. 다만 ③(목록 조회)보다는 **먼저 끝나게** 그대로 두었습니다. 같이 돌리면 방금 풀린 잠금이 한 주기 동안 "잠김"으로 보일 수 있기 때문입니다. 정리 작업 자체는 빼지 않았습니다. 잠금이 제때 풀려 보이게 하는 역할이 있습니다.

## 기대 효과

| 상황 | 이전 | 이후 |
|---|---|---|
| 대시보드를 보고 있을 때 | 분당 약 250번 조회 | 같음(화면은 계속 실시간) |
| **다른 탭에 가 있거나 창을 최소화** | 분당 약 250번 | **0번** |
| 다시 탭으로 돌아왔을 때 | 다음 주기까지 최대 5초 늦게 갱신 | **즉시 갱신** |
| 서버가 느릴 때 | 요청이 겹쳐 쌓일 수 있음 | 항상 한 번에 하나 |
| 숨겨진 게시글 탭 | 5초마다 계속 확인 | 멈춤. 돌아오면 바로 확인(자리를 비운 사이 달린 댓글을 즉시 알림) |

## 확인한 결과

**폴링 부품 단독 검증** — 이 프로젝트에는 자바스크립트 테스트 환경이 없어서, 가짜 브라우저(`document.hidden`, 타이머)를 만든 Node 스크립트로 `polling.js`를 돌렸습니다. 12개 항목 모두 통과했습니다.

| 확인 | 결과 |
|---|---|
| 시작하자마자 1번, 이후 5초 간격 | 15초 동안 3번 더 |
| 숨긴 60초 동안 | **0번**, 예약된 타이머도 없음 |
| 다시 보이면 | 즉시 1번, 5초 뒤 다시 1번 |
| 응답이 8초 걸릴 때 | 동시에 1개만, 간격은 응답 8초 + 대기 5초 |
| 요청 중에 숨김·복귀를 빠르게 반복 | 동시에 1개만 |
| 작업이 계속 실패 | 멈추지 않고 계속 시도 |
| `immediate: false` | 바로 실행하지 않고 한 주기 뒤 실행 |

**로컬 사이트(실제 브라우저)** — 테스트 회원으로 로그인해 게시글 화면을 열고, 브라우저의 요청 기록에서 `/comments/latest` 호출 수를 셌습니다(탭 숨김은 `document.hidden`을 바꾸고 `visibilitychange`를 보내 흉내 냄).

| 구간 | 호출 수 변화 |
|---|---|
| 보이는 상태 11초 | +2 (5초 간격) |
| **숨긴 상태 16초** | **+0** |
| 돌아온 직후 | +1 (즉시) |
| 돌아오고 5.5초 | +1 (주기 재개) |

`board.js`가 모듈로 정상 로드됐고 서버 오류는 없었습니다. 관리자 대시보드는 같은 부품을 쓰며, 로그인에 운영 관리자 비밀번호가 필요해 배포 후 직접 확인합니다(다른 탭에 다녀왔을 때 화면이 바로 갱신되면 정상).

**자동 테스트** — 660개 → **665개**, 전부 통과 (`tests/test_polling.py` 5개 신규).

| 테스트 | 확인한 것 |
|---|---|
| `setInterval` 없음 | `public/js` 어디에도 `setInterval` 폴링이 남아 있지 않음 |
| 연결 | 대시보드·게시글이 `polling.js`를 쓰고, `board.js`는 `type="module"`로 로드 |
| 겹침 방지 | 페이지 번호 보정 후 재요청을 `await` |
| 서버 정리 3종 | 세 작업이 **동시에** 돌고(셋이 모두 시작해야 풀리는 장벽으로 확인), 목록 조회는 그 **뒤에** 실행 |

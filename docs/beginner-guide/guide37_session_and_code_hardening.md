# 37단계 — 복구 코드 시도 제한 보강 + 관리자 세션 검증

[◀ 36단계](guide36_db_connection.md) · [전체 목차](beginner-guide.md)

> 코드 점검에서 두 가지 빈틈을 찾아 막았습니다. 하나는 [34단계](guide34a_email_recovery.md)의 6자리 복구 코드를 **동시에 여러 번 보내면 "5회 제한"을 넘겨 시도할 수 있던 문제**, 다른 하나는 **삭제된 관리자도 브라우저에 남은 쿠키로 대시보드를 계속 볼 수 있던 문제**입니다. DB 스키마는 바뀌지 않습니다.

## 1. 복구 코드: "비교 → 횟수 증가"를 "시도권 예약 → 비교"로

### 무엇이 문제였나

6자리 코드는 경우의 수가 100만 개뿐이라, **틀릴 수 있는 횟수(기본 5회)를 제한하는 것이 유일한 방어선**입니다. 그런데 기존 순서는 이랬습니다.

```
1. DB에서 복구 요청을 읽는다 (code_attempts = 0)
2. 입력한 코드와 비교한다
3. 틀렸으면 code_attempts를 "읽었던 값 + 1"로 저장한다
```

공격자가 서로 다른 코드 1000개를 **동시에** 보내면 어떻게 될까요?

| 순서 | 일어나는 일 |
|---|---|
| 1 | 1000개 요청이 모두 `code_attempts = 0`인 같은 행을 읽는다 |
| 2 | 1000개 모두 코드를 비교한다 → **1000번 맞춰본 셈** |
| 3 | 틀린 요청들이 전부 `code_attempts = 1`을 저장한다(서로의 증가분을 덮어씀) |

문제가 두 겹이었습니다. 증가가 원자적이지 않아서 횟수가 덮어써졌고, 그보다 더 근본적으로 **비교를 먼저 하고 횟수를 나중에 올려서**, 증가를 원자적으로 고쳐도 동시에 온 요청은 모두 비교까지 끝나 버립니다.

**비유:** 놀이기구 줄에서 "5명까지만 태운다"면서 표를 확인하지 않고 일단 다 태운 다음 인원을 세는 것과 같습니다. 표(시도권)를 **먼저** 나눠 주고, 표를 받은 사람만 태워야 합니다.

### 바꾼 순서

```
1. 시도권을 예약한다 — "code_attempts가 내가 읽은 값 그대로일 때만" +1 (조건부 UPDATE)
   · 경쟁에서 지면(0행) 다시 읽고 재시도 (최대 3회)
   · 한도 도달 / 이미 취소·사용됨 / 재시도 소진 → 예약 실패(None)
2. 예약에 성공한 요청만 코드를 비교한다
3. 틀렸고 방금 쓴 시도권이 마지막이면 요청을 취소(REVOKED)한다
```

| 상황 | 결과 |
|---|---|
| 동시에 1000개 | 시도권은 5장뿐 → **최대 5개만 비교**, 나머지는 "복구를 다시 요청해주세요" |
| 5번째 시도에 맞는 코드 | 성공 (예약 단계에서는 취소하지 않으므로) |
| 5번째 시도도 틀림 | 요청 취소 — 이후 맞는 코드를 넣어도 소용없음 |
| 경쟁이 계속돼 예약 실패 | 맞는 코드여도 통과시키지 않음(실패 쪽으로 닫힘) |

조건부 UPDATE는 [35단계](guide35_password_change.md)에서 세션 세대 번호를 올릴 때 쓴 방식과 똑같습니다. Supabase REST로는 `BEGIN/COMMIT`을 쓸 수 없어서, "WHERE 조건이 맞을 때만 고친다"는 성질로 원자성을 얻습니다.

```python
# db/recovery.py — reserve_recovery_code_attempt()
.update({"code_attempts": current + 1})
.eq("id", request_id)
.eq("status", "PENDING")
.eq("code_attempts", current)   # 읽은 값 그대로일 때만
.gt("expires_at", now)
```

### 2차 방어선: `/recovery/verify` 전용 요청 제한

코드 제출(`POST /recovery/verify`)에는 전역 한도(분당 120회)와 별개로 **IP당 분당 10회**(`RECOVERY_VERIFY_RATE_LIMIT_PER_MINUTE`) 한도를 걸었습니다. 넘으면 429로 거절하고 `HTTP_FLOOD` 이벤트로 기록됩니다. limiter가 `app.py`에서 만들어지므로 `routes/recovery.py`에 데코레이터로 달면 순환 import가 생겨서, `app.py`가 등록된 뷰 함수를 감싸는 방식으로 붙였습니다. 전역 한도와 마찬가지로 인메모리 저장소라 서버리스에서는 인스턴스마다 따로 센다는 한계가 있습니다 — 핵심 방어는 어디까지나 위의 시도권 예약입니다.

## 2. 관리자 세션: 요청마다 DB의 계정과 대조

### 무엇이 문제였나

Flask 세션은 **서명된 쿠키**입니다. 서버는 "이 쿠키를 내가 만들었는가"만 확인할 뿐, 쿠키 목록을 따로 보관하지 않습니다. 기존 문지기(`login_required`)는 쿠키에 `admin_username`이 있는지만 봤기 때문에:

| 상황 | 기존 동작 |
|---|---|
| super_admin이 관리자 계정을 삭제 | 그 사람의 브라우저 쿠키로 대시보드·`/api/status`(회원 이메일, 로그인 기록 등) **계속 조회 가능** |
| 삭제 후 같은 아이디로 다시 생성 | 옛 쿠키가 새 계정으로 **되살아남** |
| 쿠키 탈취 | 만료 시간이 없어 **무기한 사용 가능** |

쓰기 API는 `require_permission`이 role을 조회하다 "계정 없음"이면 403을 냈기 때문에 막혔지만, 조회는 열려 있었습니다.

### 바꾼 동작

로그인할 때 세션에 세 가지를 넣고, 요청마다 모두 확인합니다.

| 세션 값 | 확인하는 것 |
|---|---|
| `admin_username` | DB 계정의 아이디와 같은가 |
| `admin_id` (기본키) | 그 id의 계정이 **아직 존재하는가** — 삭제 후 재생성하면 id가 달라짐 |
| `admin_login_at` | 로그인한 지 `ADMIN_SESSION_MAX_HOURS`(기본 8시간)가 지나지 않았는가 |

하나라도 어긋나면 관리자 세션 값을 지우고 로그인 화면(API는 401)으로 돌려보냅니다. 수명은 "마지막 활동"이 아니라 **로그인 시각 기준**입니다 — 대시보드가 5초마다 폴링하므로 "활동 없음" 상태가 절대 생기지 않기 때문입니다. Flask의 `PERMANENT_SESSION_LIFETIME`을 쓰지 않은 것은, 회원과 관리자가 같은 쿠키를 쓰므로 회원 세션까지 영향을 받기 때문입니다.

### "세션 없음"과 "무효 세션"을 구분한다

```
세션이 아예 없음   → 지금까지처럼 미인증 접근으로 기록 + 탐지·조기 경보 (21단계, 31단계)
세션은 있는데 무효 → 기록하지 않음. 관리자 세션만 지우고 다시 로그인하게 함
```

이렇게 나누지 않으면, 삭제된 관리자의 대시보드 탭이 5초마다 `/api/status`를 부르면서 **그 관리자의 IP가 "미인증 접근 공격"으로 잡혀** Slack 알림이 울립니다.

### 덤으로 줄어든 조회

문지기가 계정을 조회할 때 role도 함께 가져와 `g.admin`에 담아 둡니다. 그래서 `require_permission`과 `/api/status`가 role을 따로 조회하지 않고, 승인/반려 API도 "누가 승인했는지" id를 다시 찾지 않습니다. 결과적으로 쓰기 API의 DB 조회 수는 그대로이고, 폴링 1회당 조회는 오히려 줄었습니다. 쓰지 않게 된 `db.get_admin_role()`은 삭제했습니다.

### 로그아웃은 관리자 세션만

관리자 로그아웃이 `session.clear()`로 **같은 브라우저의 회원 세션까지** 지우던 부수 효과도 고쳐, 이제 관리자 값만 지웁니다(회원 로그아웃이 회원 값만 지우는 것과 같은 방식).

## 배포할 때 알아둘 점

- **배포 직후 관리자는 한 번 다시 로그인해야 합니다.** 기존 세션에는 `admin_id`가 없어서 무효로 처리됩니다(의도된 동작). 대시보드는 401을 받으면 자동으로 로그인 화면으로 이동합니다.
- 새 환경변수(둘 다 선택, 기본값으로 충분): `ADMIN_SESSION_MAX_HOURS=8`, `RECOVERY_VERIFY_RATE_LIMIT_PER_MINUTE=10`
- DB 스키마·마이그레이션 변경 없음. 화면 변경 없음.

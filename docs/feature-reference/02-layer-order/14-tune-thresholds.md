# 14. 임계값 튜닝 리포트

<aside>
🎯 **한 줄 요약**
탐지 기준(예: "60초에 5회")이 **너무 예민하면** 정상 사용자까지 자주 잠기고, 관리자가 매번 풀어줘야 합니다. 이 리포트는 "혹시 우리가 너무 예민하게 설정한 건 아닐까?"를 **데이터로 점검**합니다.
</aside>

> 🗺️ **클릭해서 코드를 볼 수 있는 흐름도**: [14-tune-thresholds.html](14-tune-thresholds.html)
> 📚 **계층**: Layer 4. 관리

---

## 🏢 비유로 먼저 이해하기

| 현실 | 이 프로젝트 |
|---|---|
| 도난 경보기가 너무 예민해서 **고양이만 지나가도 울림** | 임계값이 너무 낮아 정상 사용자도 잠김 |
| 경비원이 울릴 때마다 "오작동이네" 하고 **바로 꺼버림** | 관리자가 자동 해제 전에 "즉시 해제"를 누름 |
| 한 달간 **오작동 비율 집계** | 이 리포트 |

<aside>
💡 **핵심 아이디어**
잠금은 5분 뒤 자동으로 풀립니다. 그런데 관리자가 **5분을 다 기다리지 않고 훨씬 일찍** 풀어줬다면, "정상 사용자였는데 잘못 잠갔구나"라는 신호로 볼 수 있습니다. 이를 **조기 해제**라고 부르고 그 비율을 셉니다.
</aside>

---

## 🔄 리포트가 만들어지는 순서

```bash
python scripts/management/tune_thresholds.py --days 7
```

| 순서 | 동작 | 쉬운 설명 |
|:-:|---|---|
| ① | 입력값 확인 | `--days`는 1 이상, `--early-release-ratio`는 0~1 사이 |
| ② | **해결된 CRITICAL 이벤트** 가져오기 | 지난 N일 중, 잠긴 시각과 풀린 시각이 **둘 다 있는 것만** |
| ③ | 잠금~해제 **간격 계산** | 영구 잠금은 제외 (자동 만료가 없어 이 기준이 성립하지 않음) |
| ④ | **자동 해제 시간의 50% 미만**이면 "조기 해제" | 기본: 300초 × 0.5 = **150초** 미만 |
| ⑤ | 유형별로 세고, **30% 이상이면 재검토 권장** 표시 | |
| ⑥ | 전체 합계 출력 | |

<aside>
🔍 **읽기 전용 도구입니다.**
서버 상태를 **전혀 바꾸지 않고** 기존 `security_events` 표만 조회합니다. 판단을 대신 내려주는 도구가 아니라, 판단에 **참고할 숫자**만 보여줍니다. (30%라는 기준도 정답이 있는 값이 아니라 팀이 임의로 정한 값이라, 운영하며 바꿔도 됩니다.)
</aside>

## 🧪 예시로 보기

```
===== 로그인 워치독 임계값 튜닝 리포트 (최근 7일) =====
기준: 잠금 후 150초 미만에 풀리면 '조기 해제'로 분류 (자동 해제 시간 300초의 50%)

BRUTE_FORCE: 20건 중 9건(45%) 조기 해제 <- 기준 재검토 권장
DISTRIBUTED_BRUTE_FORCE: 3건 중 0건(0%) 조기 해제

전체: 23건 중 9건(39%) 조기 해제
```

`BRUTE_FORCE`의 조기 해제 비율이 45%로 30%를 넘었으므로, **"실패 5회 기준(`FAILURE_THRESHOLD`)이 너무 예민한 건 아닌지"** 검토가 권장됩니다.

## 📖 용어 사전

<details>
<summary><b>오탐(False Positive)</b></summary>

실제로는 정상인데 "위험하다"고 잘못 판단한 경우입니다. 임계값이 너무 낮을수록 오탐이 늘어납니다.
</details>

<details>
<summary><b>조기 해제</b></summary>

자동 해제 시각이 되기 전에 관리자가 먼저 푼 경우입니다. 이 프로젝트에서는 "자동 해제 시간의 절반 미만에 풀림"으로 정의합니다.
</details>

## ⚠️ 알아둘 한계

- 관리자가 **정확히 언제 버튼을 눌렀는지** 초 단위 로그는 없어서, "자동 만료 시간의 절반 미만"이라는 **간접 지표로만 추정**합니다.
